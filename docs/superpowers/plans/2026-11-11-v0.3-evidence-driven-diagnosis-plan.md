# v0.3 证据驱动诊断工作流实施计划

**依据：** `2026-11-11-v0.3-evidence-driven-diagnosis-design.md`  
**状态：** 实施中

## 交付顺序

1. 新建 `tests/v03/`。先建立确定性领域行为的 RED 测试：请求/响应 schema、意图分类、设备上下文解析、证据引用对象与冻结结构化候选加载。
2. 将六类已审核结构化候选加载为不可变领域证据对象，保留包、来源、页码、适用性和证据定位；保持阶段 0 冻结文件不变。
3. 先测试后实现意图路由、请求设备上下文规范化以及稳定的不兼容/范围外结果；不允许资产 ID 或相似设备猜测型号。
4. 先测试后实现 `SafetyPolicyGate`：型号缺失、范围外变体、跨包、联锁旁路、能源隔离、真空释放、危险介质、参数修改与“候选根因不得表述为确定根因”。
5. 先测试后实现 `EvidenceGapDetector` 和诊断提取服务。按意图与证据类型控制确认事实、候选原因、检查步骤和所需信息。
6. 先测试后实现 DeepSeek 适配器与本地证据模板回答器：环境配置、非思考 JSON 调用、引用白名单校验、错误归一化、最多一次瞬时错误重试及无密钥/失败降级。
7. 先测试后实现真实 `StateGraph`，记录每个实际执行节点；将已装配的加载器、检索器和回答器以显式依赖传入，保证请求间状态隔离。
8. 先测试后接入 `POST /api/diagnosis/query`。API 路由必须调用编译图，返回统一协议，并在生产工厂中使用两个冻结知识包与本地检索模型；任何依赖不可用返回明确业务状态，不能跨包兜底。
9. 增加 guardrail 评测运行器，仅读取并逐条执行冻结的 `guardrail_eval_v1.jsonl`。新增端到端 API 与跨设备隔离回归。
10. 更新 `pyproject.toml`、`.env.example`、README 和进度记录：如实描述 DeepSeek 需要显式环境变量、自动化状态、真实发布验收缺口与复现命令。
11. 运行 v0.3 定向测试、所有 Python 回归、前端测试与生产构建；仅在有效密钥已通过真实请求验证时记录 `release_verified`，否则停在 `automated_verified`。

## 验证纪律

- 每个生产行为先写最小 RED 测试并实际运行确认其因缺少行为而失败。
- 每一小步 GREEN 后立即运行该测试；每个组件完成后运行对应 v0.3 测试模块。
- 任何新增测试替身只通过显式依赖注入使用，不能成为默认生产路径。
- 阶段 0 冻结包、评测题和 v0.2 报告均不改写；guardrail 只读取现有数据。
- 不将 API 密钥、认证头、完整提示词、完整受限证据或模型隐藏推理写入日志、测试产物或报告。
- `scripts/` 是现有未跟踪用户内容，不纳入本阶段改动或提交。
