# v0.6：工程化与离线交付设计

**日期：** 2026-11-18  
**状态：** 已确认设计，待实施  
**范围：** 在不修改阶段 0 冻结知识包、不公开再分发厂商资料或模型权重的前提下，将 v0.5 已验证的 Vue、FastAPI、MySQL、知识包和本地检索链路交付为可冷启动、可诊断启动失败、可离线运行、可备份恢复的完整演示栈。

## 1. 目标与发布状态

v0.6 完成后，用户应能仅依据 README 在新环境中完成以下流程：

1. 配置数据库密码、两个本地模型目录和两个冻结知识包目录；
2. 运行一条 Docker Compose 启动命令；
3. 自动完成数据库迁移、合成演示资产初始化、知识包验证和索引构建；
4. 通过 Vue 页面访问设备、诊断和工单流程；
5. 通过健康与就绪接口判断数据库、迁移、知识包、索引和模型状态；
6. 在离线模式下完成基于本地证据的诊断，不访问外部模型服务；
7. 按文档备份数据库，并在失败后恢复数据库或重建可再生索引。

代码、自动化测试和生产构建全部通过后标记 `automated_verified`。只有在无历史容器、无历史数据库卷和无历史索引卷的环境中完成真实 Docker 冷启动、离线诊断及重启恢复后，才标记 `release_verified`。

## 2. 已确认方案与边界

### 2.1 采用独立 bootstrap 服务

完整栈使用四个服务：

```text
MySQL 健康
    ↓
bootstrap 一次性任务
    ├─ Alembic upgrade head
    ├─ 幂等导入 synthetic 演示资产
    ├─ 验证冻结知识包和注册表
    ├─ 验证本地模型目录与指纹
    └─ 构建或复用不可变检索索引
    ↓ 成功退出
FastAPI API
    ↓
Vue 静态前端 / Nginx 反向代理
```

API 不在进程启动时静默迁移数据库、写入演示数据或重建索引。`bootstrap` 失败时 API 不启动，避免出现“页面可访问但诊断运行时才发现依赖缺失”的部分可用状态。

### 2.2 数据与版权边界

- `data/packs/` 中的冻结知识包属于 `local_evidence_only`，不复制进镜像、不提交 Git、不上传 CI；
- BGE-M3 和 reranker 权重不复制进镜像、不提交 Git、不上传 CI；
- Compose 只以只读挂载使用知识包和模型；
- MySQL 数据和生成索引使用独立命名卷；
- 公开镜像只包含应用代码、公开配置、前端构建产物和依赖；
- “知识包导入”指校验、注册并建立运行索引，不修改冻结包，也不把私有内容复制进公开制品。

### 2.3 本阶段非目标

- 不修改知识包内容、冻结评测集或历史评测报告；
- 不新增设备、资料、诊断功能或前端业务页面；
- 不引入 Redis、Kubernetes、云模型、对象存储或外部 CMMS/EAM；
- 不建立自动更新、自动下载模型或自动下载厂商资料的链路；
- 不进行 v0.7 的全量质量收敛或 v0.8 的全部异常注入和性能基线；
- 不把 Docker 冷启动成功扩大表述为工业现场部署能力。

## 3. 容器与网络架构

### 3.1 `db`

- 使用固定大版本的 MySQL 官方镜像，不使用浮动 `latest`；
- 数据写入命名卷，容器不向宿主机公开 3306；
- 健康检查使用容器内 MySQL 客户端；
- 数据库名、普通应用用户和密码来自 Compose 环境变量；
- 密码必须由用户在本地环境文件中显式设置，不能把本机密码或真实凭据写入仓库。

### 3.2 `bootstrap`

`bootstrap` 与 API 使用同一后端镜像和相同只读输入，但运行独立入口。任务必须幂等：重复运行迁移、演示数据初始化和索引准备不会生成重复业务数据或覆盖有效索引。

成功时输出结构化阶段结果并以 0 退出。失败时输出稳定错误码、脱敏原因和建议动作，并以非 0 退出。Compose 使用 `service_completed_successfully` 阻止依赖服务在 bootstrap 失败后启动。

### 3.3 `api`

- 继续以非 root 用户运行；
- 只读挂载知识包、本地模型和公开注册表，读写挂载索引卷；
- 通过容器服务名连接 MySQL；
- 监听容器内 8100，并仅映射到宿主机 `127.0.0.1:8100`；
- 生产入口不启用代码热重载；
- Uvicorn 和应用日志统一发送到标准输出。

### 3.4 `web`

- 使用 Node 固定大版本完成 `npm ci` 和 Vite 生产构建；
- 运行阶段只保留 Nginx 与静态文件，不携带 Node、源码依赖目录或测试文件；
- Nginx 为 Vue History 路由回退到 `index.html`；
- `/api`、`/health` 和 `/ready` 代理到 API，浏览器默认使用同源相对地址；
- 只映射宿主机 `127.0.0.1:5174`。

## 4. 配置与启动校验

现有 `Settings` 扩展为显式、带类型的运行配置，至少包含：

- `offline_mode`；
- `packs_root`；
- `pack_registry_path`；
- `indexes_root`；
- `bge_model_path`；
- `reranker_model_path`；
- 数据库 URL、请求大小、会话有效期和 DeepSeek 配置。

启动校验必须在昂贵初始化前完成，并返回稳定错误码。至少检查：

- 数字配置可解析且位于允许范围；
- 数据库 URL 使用受支持的 MySQL/PyMySQL 方案；
- 注册表、两个冻结知识包和必需文件存在；
- 知识包 manifest、记录数、来源和内容哈希通过现有加载器校验；
- 两个本地模型目录为本地绝对路径，包含可读取的 `config.json`；
- 索引目录可写，知识包和模型目录以只读方式使用；
- 离线模式与外部模型配置不冲突。

错误不得直接输出数据库 URL、环境变量全集、API Key 或宿主机敏感路径。用户可执行单独的 `preflight` 命令，在启动 Compose 前获得同样的校验结果。

## 5. 离线模式

Compose 默认设置 `INDUSTRIALOPS_OFFLINE=true`。离线模式采用“配置拒绝 + 运行时拒绝”两层保护：

1. 即使环境中存在 DeepSeek API Key，回答生成器也不构造或发送 DeepSeek 请求，而是使用现有证据约束降级回答；
2. 本地模型只能从配置的本地目录加载，不接受模型名称或远程仓库标识；
3. 设置 `HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1` 和关闭外部 tracing 的环境变量；
4. 禁止应用启动或请求处理中自动下载模型、资料或索引；
5. 日志和就绪状态明确报告 `offline_mode=true` 与外部回答器禁用状态。

可选在线模式必须由用户显式设置 `INDUSTRIALOPS_OFFLINE=false`，并单独配置允许的 HTTPS DeepSeek 地址和密钥。在线与离线测试分别验证；不得因在线配置缺失而影响默认离线启动。

## 6. 知识包导入与索引构建

### 6.1 输入身份

每个索引版本由以下输入共同确定：

- 知识包 `pack_id` 和 `content_sha256`；
- 设备包注册表版本与文件 SHA-256；
- BGE-M3 模型指纹；
- 索引格式版本；
- 文本预处理版本。

索引 ID 由上述值确定性生成。相同输入重复运行直接复用；任一输入变化都创建新版本，不能静默覆盖旧版本。

### 6.2 索引产物

每个包的索引目录至少包含：

- `manifest.json`：索引身份、输入哈希、模型指纹、文档数、向量维度和创建时间；
- 文档 ID 顺序文件；
- 本地向量文件；
- 构建完成标记。

构建先写临时目录，完成全部校验后再原子发布。中断或失败留下的临时目录不视为可用索引。API 只加载 manifest 与当前输入完全一致的完成版本。

索引只保存冻结语料的派生向量和必要元数据，仍属于本地运行产物，不上传公开仓库或 CI。索引可由知识包和模型完全重建，因此不是唯一事实来源。

### 6.3 运行时使用

移除诊断运行时硬编码的 Windows 模型路径。API 从配置路径加载查询向量模型和 reranker，并读取 bootstrap 生成的文档向量，不再在第一次诊断请求中重新编码整批候选文档。

检索仍保持严格包级隔离、型号/控制器/修订版过滤、BM25、向量、RRF 和重排语义，不改变 v0.2/v0.3 的业务契约。

## 7. 健康、就绪与启动失败

### 7.1 `/health`

`GET /health` 只报告 API 进程是否存活，不访问数据库、模型或知识包。成功固定返回 200，供容器重启策略使用。

### 7.2 `/ready`

`GET /ready` 返回当前依赖状态：

- `database`：可连接；
- `migration`：数据库 revision 等于 Alembic head；
- `knowledge_packs`：两个冻结包验证通过；
- `indexes`：两个当前索引存在且身份匹配；
- `local_models`：路径和指纹与索引一致；
- `offline_policy`：离线保护配置一致。

全部通过时返回 200 和 `status=ready`；任一必需依赖失败时返回 503、`status=not_ready`、稳定错误码和不含秘密的摘要。就绪检查不得触发迁移、模型下载或索引构建。

### 7.3 稳定启动错误

至少定义以下错误族：

- `CONFIG_*`：缺失、格式或离线冲突；
- `DATABASE_*`：连接或迁移失败；
- `PACK_*`：缺失、哈希或注册表不一致；
- `MODEL_*`：目录、文件或指纹无效；
- `INDEX_*`：构建失败、损坏或身份过期。

容器日志必须能让用户区分“需要修配置”“需要恢复数据库”“需要重新挂载资料”和“需要重建索引”。

## 8. 日志脱敏

后端采用统一日志配置和脱敏过滤器。日志必须：

- 使用结构化字段记录时间、级别、事件名、服务、请求 ID 和稳定错误码；
- 脱敏 MySQL/其他数据库 URL 中的凭据、DeepSeek Key、Bearer Token、Cookie、密码和常见 secret 字段；
- 不记录完整请求体、诊断原问题、模型提示词、模型原始响应或知识包正文；
- 第三方异常只保留允许的异常类型和脱敏摘要；
- Uvicorn access log 不记录 Authorization 头或查询参数中的秘密。

脱敏在输出 handler 前执行，不能依赖调用方自觉清洗。现有错误清洗能力作为基础扩展，不建立第二套互相冲突的规则。

## 9. CI 与自动化验证

新增 GitHub Actions 工作流，使用固定主版本执行：

1. Python 安装与全量 `pytest`；
2. 前端 `npm ci`、Vitest 和 Vite 生产构建；
3. 后端镜像与前端镜像构建；
4. `docker compose config`；
5. 不依赖私有资料或真实模型的交付契约测试。

CI 使用最小测试夹具验证知识包、索引和启动错误契约，不上传真实知识包、模型、数据库备份或环境文件。真实本地模型索引构建和完整冷启动只在发布验收环境执行。

实现遵守 TDD：每个新生产行为先写失败测试并确认失败原因，再做最小实现。至少覆盖：

- 配置校验与离线冲突；
- 离线模式即使存在 API Key 也不发起 HTTP 请求；
- bootstrap 阶段顺序、幂等和失败退出；
- 索引身份、复用、原子发布、损坏与过期检测；
- `/ready` 的 200/503 和依赖明细；
- 日志秘密脱敏；
- Compose 服务依赖、只读挂载、健康检查和非 root 运行；
- Nginx SPA 回退与同源 API 代理；
- 现有后端与前端测试全部继续通过。

## 10. 备份与失败恢复

README 和独立运维文档提供 PowerShell 5.1 可复制执行的流程。

### 10.1 必须备份

- MySQL 业务数据库：用户、会话、设备、诊断记录、工单、审批、审计和 checkpoint；
- 本地环境配置的无秘密模板，以及实际使用的知识包/模型/镜像版本记录；
- 冻结知识包和模型由用户原始本地归档负责保存，不随数据库备份公开分发。

备份文件不得提交 Git。命令不得把密码直接写进命令历史或备份文件名。

### 10.2 可重建内容

索引卷损坏或缺失时，删除精确确认的索引卷后重新运行 bootstrap。由于索引由冻结知识包和本地模型确定性生成，不要求把索引作为唯一备份。

### 10.3 恢复顺序

```text
停止 web/api
→ 验证知识包与模型版本
→ 启动 MySQL
→ 恢复数据库备份
→ 执行 Alembic upgrade head
→ 重建或验证索引
→ 启动 API 和 web
→ 检查 /health 与 /ready
→ 抽查资产、历史工单和审批 checkpoint
```

恢复文档明确区分可安全重试、需要重建索引和需要人工恢复数据库的故障，不提供会静默删除数据库卷的“一键修复”。

## 11. README 冷启动流程

README 的完整栈入口以 Windows PowerShell 5.1 为准，至少包含：

1. 软件版本要求和 Docker Desktop 状态检查；
2. 从模板创建本地环境文件；
3. 配置数据库密码、本地知识包路径和两个模型路径；
4. 执行 `docker compose config` 和 preflight；
5. 执行完整栈构建与启动；
6. 查看 bootstrap 结果、容器状态、`/health` 和 `/ready`；
7. 打开 `http://127.0.0.1:5174` 完成两设备演示；
8. 验证离线回答器状态；
9. 安全停止服务，并说明保留卷与删除卷的差异；
10. 执行备份、恢复和索引重建。

所有命令必须与真实服务名、端口、路径和环境变量一致。README 只能声明已完成相应自动化或真实发布验收的能力。

## 12. 发布验收

自动化验收通过后，在用户启动 Docker Desktop 的真实 Windows 环境执行：

1. 确认没有本项目历史容器、数据库卷和索引卷；
2. 使用现有本地知识包和模型按 README 完成 Compose 冷启动；
3. 核对 bootstrap 完成迁移、初始化和两个包的索引构建；
4. 核对 `/health=200`、`/ready=200` 及全部依赖状态；
5. 在离线模式、不提供 DeepSeek Key 的条件下完成 CNC 和真空泵各一次诊断；
6. 核对引用未跨包、回答明确使用证据降级且没有外部模型调用；
7. 创建工单草稿，重启 API，再按原 `thread_id` 完成审批；
8. 执行数据库备份，验证索引重建流程和数据库恢复说明；
9. 保存不含秘密的 v0.6 验收报告。

当前环境已检测到 Docker CLI 29.6.1 和 Docker Compose v5.1.4，但 Docker Desktop Linux 引擎尚未运行。该事实不阻止设计和实现；真实冷启动未执行前，v0.6 不得标记为 `release_verified`。
