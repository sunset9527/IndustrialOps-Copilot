# v0.3：证据驱动诊断工作流设计

**日期：** 2026-11-11  
**状态：** 已批准，待实施  
**范围：** 在不修改阶段 0 冻结知识包的前提下，将 v0.2 的工业检索接入真实 LangGraph 诊断主链路，并增加确定性兼容性校验、安全门控、证据缺口检测、DeepSeek 结构化回答及无 LLM 降级路径。

## 1. 目标与完成状态

v0.3 将 v0.2 的设备包加载与工业检索能力接入诊断 API，使一次请求真实经过 LangGraph，并以兼容证据为唯一事实来源。完成后系统应满足：

- 型号不明时不生成型号相关确定性建议；
- 证据不足时不生成确定性根因或维修步骤；
- 高风险请求由本地确定性规则拦截，DeepSeek 无权覆盖；
- DeepSeek 不可用、响应非法或引用越界时，返回同一协议的本地证据回答；
- CNC 与真空泵的知识、规则和引用保持严格隔离。

本阶段完成代码和自动化测试后标记 `automated_verified`。只有使用本地 BGE-M3、bge-reranker-base 和真实 DeepSeek API 完成正常回答及 LLM 失败降级验证后，才标记 `release_verified`。缺少真实密钥或真实调用未完成时不得宣称发布验收通过。

## 2. 已确认决策与边界

### 2.1 已确认决策

- 采用“确定性工作流控制，DeepSeek 只负责组织回答”的架构。
- 设备解析、知识包选择、兼容性校验、安全门控、证据充分性及最终引用均由本地代码决定。
- DeepSeek 默认模型为 `deepseek-flash`，可通过环境变量切换为 `deepseek-v4-pro`。
- DeepSeek 使用 OpenAI 兼容的 Chat Completions 接口、非思考模式和 JSON 输出。
- 只向 DeepSeek 发送本次请求中少量、已通过兼容性校验的证据片段，不发送整本手册。
- DeepSeek 返回的每项事实、候选原因和步骤都必须声明 `evidence_ids`；本地代码按批准证据集合再次校验。
- 无密钥、超时、限流、服务异常、空白响应、非法 JSON、输出截断或越界引用均进入本地证据模板降级路径。
- 阶段 0 冻结知识包保持字节级只读。v0.3 只扩展加载后的领域对象和运行时索引，不回写冻结文件。
- API 主链路使用真实 `StateGraph`，不能以顺序调用函数后伪造 LangGraph 轨迹。

### 2.2 本阶段非目标

- 不实现设备台账、真实资产解析或数据库迁移；请求中的 `asset_id` 仅预留，不用于推断设备型号。
- 不实现工单状态机、工单草稿落库、人工审批、checkpointer、暂停、恢复或线程状态 API。
- `work_order_draft` 意图只返回能力边界提示，不提前实现 v0.4 功能。
- 不实现前端诊断工作台、证据侧栏或安全提示页面。
- 不修改知识包、冻结评测集、预期证据或 v0.2 基线结果。
- 不引入知识图谱、图数据库、Graph Agent、预测性维护或设备控制能力。

## 3. 总体架构

```text
POST /api/diagnosis/query
        │
        ▼
FastAPI 请求校验与依赖注入
        │
        ▼
LangGraph StateGraph
  ├─ IntentRouter
  ├─ EquipmentContextResolver
  ├─ EvidenceRetriever
  ├─ CompatibilityValidator
  ├─ FaultDiagnosisService
  ├─ SafetyPolicyGate
  ├─ EvidenceGapDetector
  └─ AnswerComposer
        ├─ DeepSeekAnswerGenerator
        └─ EvidenceFallbackComposer
        │
        ▼
结构化 DiagnosisResponse
```

工作流节点各自只承担一项职责。节点之间只通过 `DiagnosisState` 交换结构化数据，不依赖模块级可变状态。编译后的图由应用依赖容器持有，每个请求创建独立初始状态。

## 4. 状态与 API 契约

### 4.1 `DiagnosisState`

状态至少包含以下分组：

- 请求：`request_id`、`question`、`pack_id`、可选 `asset_id`、型号、控制器和文档修订版；
- 解析：意图、规范化设备上下文、缺失信息和解析轨迹；
- 证据：原始检索结果、兼容证据、被排除证据及稳定排除原因；
- 诊断：已确认事实、证据支持的候选原因和建议检查步骤；
- 门控：风险级别、命中规则、证据缺口、允许输出字段和是否需要人工升级；
- 输出：引用、结构化回答、回答来源和降级原因；
- 追踪：实际经过的节点、稳定错误码和安全的运行元数据。

状态不得保存 DeepSeek API 密钥、原始认证头、模型隐藏推理过程或未经清洗的异常文本。

### 4.2 请求契约

`POST /api/diagnosis/query` 接受：

```json
{
  "question": "VF-2 主轴异常噪声，应该怎么检查？",
  "pack_id": "cnc_pack_v1.0.0",
  "model": "VF-2",
  "controller": "NGC",
  "document_revision": null
}
```

`question` 和 `pack_id` 必填。型号、控制器和文档修订版是显式约束；缺失值表示未知，不得从另一个设备包或相似型号猜测。请求指定未知知识包或明确不兼容型号时，返回稳定业务状态，不进行跨包兜底。

### 4.3 响应契约

响应固定包含：

- `request_id`、`status` 和 `intent`；
- `confirmed_facts`；
- `candidate_causes`；
- `inspection_steps`；
- `safety_prerequisites`；
- `uncertainties`；
- `required_information`；
- `escalation_conditions`；
- `citations`；
- `generation`，声明提供方、模型、是否降级及安全的降级原因；
- `workflow_trace`，证明请求真实经过 LangGraph 节点。

`status` 只允许：

- `answered`；
- `needs_information`；
- `insufficient_evidence`；
- `blocked`；
- `out_of_scope`；
- `service_error`。

DeepSeek 与本地降级回答共用同一响应协议。`citations` 由本地批准证据生成，至少包含证据 ID、知识包、来源 ID、文档修订版、页码和证据定位；不接受模型自造的来源、页码或 URL。

## 5. 组件设计

### 5.1 `IntentRouter`

意图集合固定为：

- `manual_query`；
- `alarm_lookup`；
- `fault_diagnosis`；
- `maintenance_plan`；
- `work_order_draft`；
- `out_of_scope`。

路由器使用可测试的本地规则和告警码模式，输出意图与判定依据。DeepSeek 不参与安全关键路由。无法可靠归类且不属于工业运维范围时返回 `out_of_scope`；多个工业意图同时出现时按明确告警、明确故障诊断、保养查询、手册查询的稳定优先级选择，并保存命中的规则。

### 5.2 `EquipmentContextResolver`

解析器以请求中的 `pack_id` 为信任边界，从版本化设备包注册表读取设备类别、厂商、允许型号、控制器和来源版本范围。它可以规范化已声明别名，但不能把 `asset_id`、相似型号或问题中的模糊词强制映射为确定型号。

请求明确给出的型号、控制器或版本不在知识包声明范围时，记录不兼容状态并停止正常诊断。维修、拆卸、参数修改等型号相关请求缺少型号时，进入 `needs_information` 或安全阻断路径。

### 5.3 `EvidenceRetriever`

检索始终限定单一 `pack_id`。正常路径复用 v0.2 的别名增强、告警精确索引、BM25、BGE-M3、RRF 和 CrossEncoder 重排：

1. 告警码存在时先执行结构化精确检索；
2. 在兼容性条件下执行 BM25 与向量召回；
3. 通过 RRF 融合并重排；
4. 返回带来源、适用范围和分数轨迹的候选证据。

精确告警不存在时可以补充语义相似证据，但必须标记为 `semantic_only`，后续不得将其表述为当前告警的确定含义。生产路径不得以假向量或测试评分器静默替代本地模型；检索依赖不可用时返回 `service_error`，不伪造完整诊断。

### 5.4 `CompatibilityValidator`

兼容性校验在诊断提取前再次执行，验证每条候选的：

- 知识包；
- 设备类别；
- 型号；
- 控制器；
- 文档修订版；
- 来源白名单。

不兼容候选进入 `excluded_evidence` 并带稳定原因，不能进入 DeepSeek 提示、诊断字段或最终引用。若用户要求跨设备借用资料，直接命中安全规则，不切换知识包。

### 5.5 `FaultDiagnosisService`

知识包加载对象扩展为通用审核候选，支持以下冻结类型：

- `alarms`；
- `components`；
- `symptoms`；
- `failure_modes`；
- `maintenance_tasks`；
- `safety_rules`。

服务只从兼容证据和审核通过的结构化候选中建立可供回答器选择的事实集合。候选原因保持“可能”语义，不提升为确定根因。检查步骤只有在存在适用 `maintenance_tasks` 证据并通过安全门控时才进入允许输出集合。

### 5.6 `SafetyPolicyGate`

确定性门控至少实现以下稳定规则：

| 规则 ID | 行为 |
|---|---|
| `MODEL_REQUIRED` | 型号未知且请求型号相关维修时，禁止输出维修建议并请求补充型号 |
| `MODEL_OR_VARIANT_OUT_OF_SCOPE` | SMTC、nXDS C/R 变体等冻结范围外配置拒绝回答 |
| `CROSS_PACK_EVIDENCE` | 阻止 CNC 与真空泵跨包借用证据 |
| `SAFETY_INTERLOCK_BYPASS` | 旁路防护门或安全联锁的请求直接阻断 |
| `ENERGY_ISOLATION_REQUIRED` | 未停机、断电或挂牌上锁时不提供拆卸、电气或机械检查步骤 |
| `VACUUM_RELEASE_REQUIRED` | 真空系统未泄压或介质不明时不提供拆卸步骤 |
| `HAZARDOUS_MEDIA_ESCALATION` | 高温、高压、有毒、易燃或腐蚀性介质升级人工 |
| `CONTROL_PARAMETER_CHANGE` | 直接修改控制参数的请求升级人工 |
| `ROOT_CAUSE_NOT_CONFIRMED` | 证据只支持候选原因时禁止输出确定根因 |

规则输出风险级别、用户可见说明、禁止字段、所需前置条件和升级人工条件。AnswerComposer 只能消费门控后的允许字段。

### 5.7 `EvidenceGapDetector`

证据充分性按意图与证据类型判断，不以任意相关度阈值代替业务规则：

- `manual_query`：至少一条型号、控制器和版本均兼容的正文证据；
- `alarm_lookup`：精确告警证据才能解释当前代码；只有语义相似结果时必须声明不确定性；
- `fault_diagnosis`：至少存在症状或故障模式证据；要输出检查步骤，还必须存在相应维护与安全证据；
- `maintenance_plan`：必须存在适用型号和版本的维护任务证据；
- `work_order_draft`：返回 v0.4 能力边界，不生成草稿；
- `out_of_scope`：不调用 DeepSeek 生成领域答案。

缺少必需证据时，从允许字段中删除对应原因或步骤，返回 `required_information`、`uncertainties` 和人工升级条件。检索到相关文本不等于证据充分。

### 5.8 `DeepSeekAnswerGenerator`

适配器使用以下环境变量：

```text
INDUSTRIALOPS_DEEPSEEK_API_KEY
INDUSTRIALOPS_DEEPSEEK_BASE_URL=https://api.deepseek.com
INDUSTRIALOPS_DEEPSEEK_MODEL=deepseek-flash
INDUSTRIALOPS_DEEPSEEK_TIMEOUT=20
INDUSTRIALOPS_DEEPSEEK_MAX_TOKENS=1600
```

请求采用非思考模式和 JSON 输出。系统提示明确要求输出 JSON、声明字段结构和证据 ID 约束。模型输入只包含用户问题、已解析设备上下文、门控后的允许字段和少量批准证据片段。

适配器执行以下校验：

1. HTTP 请求成功且响应结构完整；
2. `finish_reason` 不表示截断、内容过滤或资源不足；
3. 内容非空白且为合法 JSON；
4. 字段符合本地 schema；
5. 每个事实、候选原因和步骤都带非空 `evidence_ids`；
6. 所有 `evidence_ids` 都属于本次批准集合；
7. 输出字段未违反安全门控和证据缺口裁剪结果。

模型只负责改写与组织，不能新增门控前不存在的诊断项。最终引用由本地证据 ID 反查生成。

### 5.9 `EvidenceFallbackComposer`

以下任一情形触发降级：

- 未配置 API 密钥；
- DeepSeek 客户端依赖不可用；
- 超时、连接失败、429 或 5xx；
- 401、402、400、422 等不可重试错误；
- 空白响应、非法 JSON、schema 不匹配、输出截断或越界引用。

降级回答器按固定模板投影门控后的结构化事实，不调用其他模型，也不扩大证据范围。响应的 `generation.provider` 为 `evidence_fallback`，`fallback_used` 为 `true`，并返回稳定、无敏感信息的原因码。

## 6. LangGraph 数据流与条件边

```text
START
  → intent_router
      ├─ out_of_scope → answer_composer → END
      ├─ work_order_draft → answer_composer → END
      └─ industrial_intent
           → equipment_context_resolver
               ├─ incompatible/out_of_scope → safety_policy_gate
               └─ compatible_or_unknown
                    → evidence_retriever
                    → compatibility_validator
                    → fault_diagnosis_service
                    → safety_policy_gate
                    → evidence_gap_detector
                    → answer_composer
                    → END
```

安全门控必须位于回答生成之前。即使前序节点或 DeepSeek 失败，最终响应仍通过同一门控结果生成。工作流轨迹来自实际节点执行记录，不能由 API 路由硬编码。

## 7. 错误处理与隐私边界

- 知识包缺失、哈希错误、注册表错误或本地检索依赖不可用时返回 `service_error`，不使用另一个包兜底。
- DeepSeek 失败不等同于诊断服务失败；只要本地兼容证据存在，就返回证据模板降级结果。
- 对瞬时超时、429 和 5xx 最多执行一次有上限的重试；401、402、400 和 422 不重试。
- 日志只记录请求 ID、模型名、耗时、状态码类别、稳定错误码、证据数量和是否降级。
- 日志、API 响应和测试产物不得包含密钥、Authorization 头、完整提示词、整段受限手册正文或 DeepSeek 原始错误正文。
- DeepSeek 调用的证据片段必须受数量和字符上限约束，并保留本地证据 ID 以便审计。

## 8. 依赖与应用装配

- `langgraph` 是 v0.3 的运行依赖，因为主链路必须真实经过 `StateGraph`。
- HTTP 客户端是 DeepSeek 适配器的运行依赖；不依赖 LangChain LLM 封装。
- 应用工厂通过依赖容器装配知识包加载器、检索器工厂、DeepSeek 适配器和编译工作流。
- 单元测试注入确定性检索器和 HTTP transport；测试替身不能进入默认生产工厂。
- 本地 BGE-M3 与 reranker 继续从既有显式路径离线加载，不能因为 DeepSeek 已接入而改用远程嵌入或远程重排。

## 9. 测试策略

实现严格采用测试先行，并逐项观察预期失败后再写生产代码。

1. **意图分类**：六种意图、告警优先级、模糊请求与知识域外问题。
2. **设备解析**：别名规范化、缺少型号、未知型号、C/R 变体和 SMTC 范围外配置。
3. **兼容性**：知识包、型号、控制器、版本和来源白名单；不兼容证据被排除且不可引用。
4. **安全规则**：每个稳定规则 ID 都有正例、反例及组合场景。
5. **证据缺口**：按意图检查必需证据；缺少维护或安全证据时删除检查步骤。
6. **DeepSeek 适配器**：合法 JSON、空白响应、非法 JSON、截断、非法引用、超时、401、402、429 和 5xx。
7. **降级回答**：无密钥和 LLM 失败时协议不变，引用仍来自批准证据。
8. **LangGraph**：节点顺序、条件边、请求间状态隔离和实际执行轨迹。
9. **API 契约**：`/api/diagnosis/query` 真实调用编译图，业务状态与 HTTP 错误边界一致。
10. **冻结规则集**：五条 `guardrail_eval_v1.jsonl` 分别得到原定 `refuse`、`escalate` 或 `insufficient_evidence` 语义结果。
11. **设备隔离**：CNC 请求不能返回真空泵证据，真空泵请求不能返回 CNC 证据。
12. **回归**：阶段 0、v0.1、v0.2、现有前端测试和生产构建全部通过。

真实发布验收另外执行：

- 使用本地 BGE-M3 与 reranker 跑通至少一个 CNC 和一个真空泵正常诊断请求；
- 使用真实 `deepseek-flash` 完成结构化回答并验证所有引用可回溯；
- 在无密钥或注入可控失败的真实 API 主链路中验证证据降级；
- 保存不含密钥和受限全文的验收记录，声明模型、知识包、注册表和代码版本。

## 10. 验收标准

v0.3 只有同时满足以下条件才达到 `automated_verified`：

1. `/api/diagnosis/query` 的真实主链路经过编译后的 LangGraph；
2. 六种意图具有确定性分类和测试；
3. 设备包、型号、控制器和文档版本不兼容时不会进入正常诊断；
4. 型号不明的型号相关维修请求不输出确定性建议；
5. 证据不足时不输出确定性根因和维修步骤；
6. 九类确定性安全规则不可被 DeepSeek 绕过；
7. DeepSeek 每项结论的证据 ID 均经过本地白名单校验；
8. DeepSeek 不可用或输出非法时返回同协议的本地证据回答；
9. 五条冻结 guardrail 评测全部符合原预期；
10. 不存在已知跨设备错误引用；
11. 阶段 0、v0.1、v0.2 和前端回归测试通过；
12. README 如实区分实现、自动化验证和真实发布验收状态。

只有再完成本地真实检索模型与真实 DeepSeek API 验证，才将 v0.3 标记为 `release_verified`。

## 11. 已知限制与下一阶段入口

- v0.3 不保存跨请求诊断状态，不提供恢复执行；
