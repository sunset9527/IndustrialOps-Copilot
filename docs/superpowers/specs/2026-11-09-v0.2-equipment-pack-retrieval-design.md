# v0.2：设备知识包与工业检索设计

**日期：** 2026-11-09  
**状态：** 实施中  
**范围：** 在不修改阶段 0 冻结知识包的前提下，实现双设备知识包加载、工业元数据过滤、告警码精确检索、别名增强和可复现的本地模型检索基线。

## 1. 目标与完成状态

v0.2 将 v0.1 的通用检索原语接入两个已冻结知识包：

- `cnc_pack_v1.0.0`；
- `dry_vacuum_pump_pack_v1.0.0`。

本阶段完成后应达到 `automated_verified`，并在真实加载本地 BGE-M3 与 bge-reranker-base、生成可审计评测报告后达到本阶段的 `release_verified`。不得以注入式测试向量、假评分器或静默降级结果冒充真实模型基线。

## 2. 决策与边界

### 2.1 已确认决策

- 采用 IndustrialOps 原生检索层，不整体迁入 HeritageMind 的领域检索模块，也不在本阶段引入 LangChain 或 ChromaDB。
- 阶段 0 冻结包保持字节级只读；v0.2 不向 `manifest.json`、`corpus.jsonl` 或 `structured_candidates_auto_reviewed.jsonl` 回写字段。
- 冻结语料缺少的设备、型号、控制器和文档版本元数据，由版本化的外部设备包注册表补齐；注册表属于 v0.2 索引配置，不属于厂商证据。
- CNC 和真空泵分别加载、分别建索引、分别评测。检索入口必须先选定知识包，不允许跨包兜底。
- 常规自动化测试使用小型确定性样例和注入式模型适配器；真实基线命令必须显式加载本地模型，并拒绝静默降级。
- 所有公开指标只来自冻结的 `data/evaluation/scenario_eval_v1.jsonl`；不删题、不补题、不改变允许证据来迎合结果。

### 2.2 本阶段非目标

- 不实现诊断 API、LangGraph 诊断主链路、证据缺口判断或结构化回答。
- 不实现安全门控、工单、人工审批、数据库台账或工业前端。
- 不新增设备、厂商手册、评测题或知识包版本。
- 不把别名、模型生成文本或查询扩展词写入证据正文。
- 不把本地索引、模型权重或受限语料打包进公开 Docker 镜像。

## 3. 数据与配置

### 3.1 设备包注册表

新增版本化 JSON 注册表，至少包含：

```json
{
  "registry_version": "v1",
  "packs": {
    "cnc_pack_v1.0.0": {
      "equipment_type": "cnc_vertical_machining_center",
      "manufacturer": "Haas",
      "models": ["VF-2"],
      "controller": "NGC",
      "equipment_aliases": ["VF2", "VF 2", "Haas VF-2"],
      "component_aliases": {},
      "sources": {
        "HAAS-OP-EN-2025": {
          "document_revision": "2025",
          "applicable_models": ["VF-2"],
          "controller": "NGC"
        }
      }
    }
  }
}
```

正式注册表必须覆盖两个冻结包的全部 `source_id`。真空泵包声明标准型号 `nXDS6i`、`nXDS10i`、`nXDS15i` 和 `nXDS20i`；没有独立控制器兼容性含义时使用显式的 `not_applicable`，不能用缺失值表示未知。

注册表中的别名只用于查询规范化和召回增强。来源适用范围必须能由现有冻结范围决策、来源名称或厂商文档标识追溯；无法确认的更细粒度适用性不得猜测。

### 3.2 统一文档对象

`EquipmentDocument` 是加载后的不可变对象，最少包含：

- `document_id`：优先使用稳定的 `chunk_id`，其次 `candidate_id`，页级冻结记录两者均缺失时使用其稳定 `unit_id`；
- `pack_id`、设备类型、厂商、适用型号和控制器；
- `source_id`、来源文件、来源 SHA-256、文档修订版、页码和证据定位；
- `text`、`text_zh`、原始语言和翻译状态；
- 原始记录 ID 与索引配置版本。

证据字段来自冻结语料；工业适用性字段来自版本化注册表。两类来源在对象和报告中保持可区分。
`source_record_id` 优先保留候选来源链（`candidate_id`、`parent_candidate_id`），缺失时回退 `unit_id` 或 `chunk_id`。该回退规则仅适配阶段 0 已冻结的页级/分块记录形态，不重写冻结文件。

## 4. 组件设计

### 4.1 `EquipmentPackLoader`

加载器执行以下确定性校验：

1. 知识包目录、清单、语料和结构化候选文件存在；
2. `pack_id` 与目录名、注册表键和每条记录一致；
3. 清单声明的语料、结构化候选和来源数量与实际一致；
4. 每条记录的 `source_id`、来源文件和来源哈希与清单一致；
5. 正式语料只包含允许的适用性状态；
6. 结构化索引只读取 `auto_reviewed_include` 记录；
7. 使用阶段 0 冻结器相同的规范化规则重算 `content_sha256`；
8. 注册表完整覆盖知识包和来源。

任一校验失败均抛出带稳定错误码的加载错误，不返回部分知识包。错误信息可以暴露包 ID、来源 ID 和校验类型，但不输出受限证据正文。

### 4.2 `EquipmentMetadataFilter`

过滤器在任何排序算法之前执行，支持：

- 知识包；
- 设备类型；
- 型号；
- 控制器；
- 文档修订版。

过滤值先做大小写、空白和连字符规范化，再按注册表中的规范值精确匹配。查询未指定某个维度时不额外缩小结果；查询明确指定且不兼容时返回空候选集合。不得为了获得结果而去掉型号、控制器或版本条件，也不得切换到另一个知识包。

### 4.3 `AlarmCodeIndex`

告警索引只使用审核通过且 `candidate_type == "alarms"` 的结构化记录。它应：

- 规范化 `ALARM`、`报警`、空白和分隔符等展示差异；
- 保留数字、字母和小数点等告警标识语义；
- 以完整规范化代码查找，不做子串命中；
- 在同一代码有多条证据时返回稳定排序的全部候选；
- 始终服从知识包和工业元数据过滤。

告警精确命中作为独立可评测通道，同时可以进入 RRF 候选；它不绕过后续兼容性过滤。

### 4.4 `AliasEnhancer`

别名增强分为设备、型号、控制器和部件四类。增强器只产生规范化查询及附加检索词，不改写原始问题，不把别名当作证据，也不改变告警代码。

增强结果包含触发的别名规则和注册表版本，供评测追踪。为避免泛化污染，每条别名只在所属知识包内生效，部件别名不得跨设备复用。

### 4.5 模型适配器与索引

- BM25 使用可测试的中英文规范化与分词接口，输出稳定分数和文档 ID 排序。
- BGE-M3 适配器从 `E:\huggingface\model` 离线加载，验证输出为 1024 维、有限且非零的向量。
- CrossEncoder 适配器从 `E:\huggingface\bge-reranker-base` 离线加载，对同一批 RRF 候选逐对评分。
- RRF 使用固定参数融合 BM25、向量及可选的告警精确通道；相同分数按文档 ID 确定性打破平局。
- 两个知识包生成互相独立的索引快照。快照记录包哈希、注册表哈希、模型指纹、分词与归一化版本、向量维度、RRF 参数和候选数量。

真实评测模式要求模型适配器返回 `loaded_from_local=true` 和模型指纹。BGE-M3 或重排模型不可用、维度异常或评分失败时，命令以失败结束，不生成该方法的成功指标。

## 5. 检索数据流

```text
指定 pack_id 与可选兼容性条件
→ 加载并验证冻结知识包
→ 规范化设备、型号、控制器和版本条件
→ 预过滤候选
→ 查询别名增强
→ 告警码精确检索（存在显式代码时）
→ BM25 与 BGE-M3 分别召回
→ 固定参数 RRF 融合
→ bge-reranker-base 重排
→ 返回带证据定位、过滤轨迹和分数轨迹的结果
```

检索结果不得只返回裸 ID。每条结果至少包含文档 ID、包 ID、来源 ID、页码、证据定位、各阶段排名或分数，以及最终排名。

## 6. 评测设计

### 6.1 数据边界

评测运行器只读取冻结的 `scenario_eval_v1.jsonl` 中 `expected_outcome == "retrieve"` 的六条场景题，并按 `expected_pack_id` 分成 CNC 和真空泵两套评测。`guardrail_eval_v1.jsonl` 属于后续安全和工作流阶段，不在 v0.2 伪造拒绝或升级结果。

### 6.2 方法与指标

每个知识包分别报告：

- BM25；
- BGE-M3 向量检索；
- RRF；
- RRF 后 CrossEncoder 重排；
- 对存在明确告警代码的测试用例报告告警码精确检索；若冻结场景集没有此类题，只报告该通道“无适用冻结题”，不自行新增评测题或计算虚假指标。

每种适用方法保存 Hit@1、Hit@3、Hit@5、MRR、nDCG@5、允许来源命中和允许页码命中。相关性为冻结评测集中声明的允许来源与页码二元判断；报告必须同时保存逐题排名，避免汇总值掩盖失败。

### 6.3 结果可追溯性

每次真实运行生成不可覆盖的结果文件，至少记录：

- UTC 时间和项目版本；
- 评测文件 SHA-256；
- 两个知识包 ID 与内容哈希；
- 注册表和索引快照哈希；
- 嵌入模型与重排模型指纹；
- 完整检索参数；
- 逐题候选、排名、来源和页码；
- 汇总指标、失败样本和运行错误。

结果中不保存模型密钥、机器用户名、不必要的绝对路径或受限手册全文。若运行失败，保存独立失败记录，但不得把缺失方法标为 0 分后宣称完整基线完成。

## 7. 依赖与离线运行

模型运行依赖以独立可选依赖组安装，避免常规 API 和单元测试强制加载大型模型。真实基线使用显式命令和模型路径，并设置本地文件模式，禁止访问远程模型服务。

自动化测试不要求真实模型权重，但发布验收必须在本机真实加载两个模型并完成六条冻结场景题。模型缺失、依赖缺失或离线加载失败时，v0.2 保持 `automated_verified`，不能标记 `release_verified`。

## 8. 测试策略

实现严格采用测试先行。测试分层如下：

1. **加载与完整性**：双包独立加载；缺文件、错误计数、记录跨包、未知来源、来源哈希或内容哈希变化会失败。
2. **过滤**：设备、型号、控制器和文档版本匹配；明确不匹配返回空；`not_applicable` 与未知状态可区分。
3. **告警索引**：展示形式归一化、完整代码匹配、重复证据稳定排序、跨包隔离。
4. **别名增强**：设备和部件别名只在所属包生效，原查询和告警码保持不变。
5. **检索组合**：BM25、向量、RRF 和重排的顺序、候选边界、平局规则和分数轨迹正确。
6. **评测与指标**：只读取冻结题；指标公式、允许来源和页码判断正确；报告包含所有版本与哈希。
7. **真实模型集成**：显式标记的本地集成测试验证 1024 维 BGE-M3、真实 CrossEncoder 分数和禁止静默降级。
8. **回归**：阶段 0、v0.1 和 v0.2 自动化测试全部通过，现有前端测试和构建不因 v0.2 退化。

## 9. 验收标准

v0.2 只有同时满足以下条件才完成：

1. 两个冻结知识包通过完整性和内容哈希校验后独立加载；
2. CNC 查询不返回真空泵资料，真空泵查询不返回 CNC 资料；
3. 设备、型号、控制器和文档版本过滤具有自动化测试；
4. 告警码精确检索只命中完整代码和兼容范围；
5. 设备与部件别名增强可追踪且不改变证据；
6. BM25、BGE-M3、RRF 和真实重排对冻结题产生可重复的逐题结果；
7. 两套设备包指标分别报告，且全部来自冻结评测集；
8. 报告保存知识包、评测、注册表、索引和模型指纹；
9. 不存在模型未加载却输出真实模型指标的路径；
10. README 如实区分已实现、自动化验证和真实模型发布验收状态。
