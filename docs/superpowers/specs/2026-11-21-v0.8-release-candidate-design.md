# v0.8：Release Candidate 发布候选验收设计

**日期：** 2026-11-21  
**状态：** 已确认设计，待书面规格复核  
**范围：** 在不增加设备、资料或产品功能的前提下，以隔离的新环境验证 IndustrialOps Copilot 是否能仅依据仓库文档完成部署、运行、理解、演示、异常恢复和结果复现。

## 1. 目标与发布状态

v0.8 是发布候选验收阶段，不是功能开发阶段。验收对象是 v0.7 已收敛的代码、两个阶段 0 冻结知识包、既有评测集、数据库迁移、Docker 交付链路和公开文档。

本阶段需要回答以下问题：

1. 第一次获取项目的使用者能否仅根据 README 和运行手册完成预检、安装、无缓存启动和验证；
2. 数据库迁移、合成演示数据、知识包校验和索引构建是否真实执行；
3. 离线模式是否阻止未经允许的外部访问，并在模型或依赖缺失时给出明确错误；
4. 认证、权限、审计、安全门控、引用隔离、工单审批和恢复是否在真实部署中保持有效；
5. 异常依赖是否产生稳定状态、脱敏日志、用户可理解提示和可执行恢复路径；
6. README、API 文档、架构说明、许可证和数据边界是否与真实主链路一致；
7. 启动时间、典型请求延迟、资源占用和小规模并发的真实基线是什么。

代码、自动化测试和静态交付检查通过后，只能标记为 `automated_verified`。只有隔离无缓存 Docker 冷启动、真实 HTTP、真实浏览器、故障矩阵、全量回归和文档真实性审计全部通过，才能标记为 `release_verified`。任何未执行、跳过或因环境受阻的强制项都必须保留原状态，不能包装成通过。

## 2. 已确认方案与隔离边界

采用“可复现 RC 验收器 + 真实环境验收”的方案，不使用纯人工清单，也不把私有知识包和本地模型放入公共 CI。

### 2.1 隔离规则

- 每次真实验收使用唯一运行 ID、独立 Compose 项目名、独立容器、独立网络、独立数据库卷和独立索引卷；
- 端口通过 RC 覆盖配置显式指定，启动前检查冲突；
- 验收器只允许操作带本次运行 ID 的资源，拒绝停止、删除或重建既有 `industrialops` 项目资源；
- 冻结知识包和本地模型继续以只读宿主机挂载使用，不复制进镜像、报告或 Git；
- 默认不自动清理失败现场。失败时保留容器、日志和报告，清理由操作者依据精确项目名显式执行；
- 不修改阶段 0 冻结包、评测题、真实结果或指标口径；发现知识包事实错误时停止验收，按知识包版本规则另行处理。

### 2.2 实现边界

新增独立的 v0.8 发布验收模块和运行文档。验收逻辑不进入诊断、检索、审批等业务模块。只有验收暴露现有发布阻断问题时，才允许在原模块中进行带回归测试的最小修复。

本阶段不增加新设备、新知识、新产品页面、新业务接口、外部 CMMS/EAM 集成、实时设备控制或预测维护能力。

## 3. 组件设计

### 3.1 RC 验收命令

提供单一入口运行 v0.8 验收。入口按阶段执行，并允许在排障时只重跑明确的非破坏性阶段：

1. `preflight`：环境与输入预检；
2. `cold_start`：隔离、无缓存构建与全新卷启动；
3. `http_demo`：真实 HTTP 主链路；
4. `fault_matrix`：受控故障注入与恢复；
5. `baseline`：启动、延迟、资源和并发采样；
6. `truth_audit`：文档、主链路、许可证和数据声明核对；
7. `finalize`：汇总不可覆盖的报告。

命令不得根据本机历史缓存、既有数据库或既有索引得出冷启动通过结论。每个阶段必须把开始时间、结束时间、状态、稳定原因码和脱敏证据摘要写入同一运行报告。

### 3.2 预检器

预检记录 Git 提交、工作树状态、Python、Node、Docker 和 Compose 版本，并验证：

- Docker 引擎可用；
- RC 项目名和端口未被占用；
- 两个冻结知识包存在且能通过现有完整性与哈希校验；
- BGE-M3 与 reranker 路径存在并包含所需配置文件；
- `.env` 所需字段完整，密码和密钥不会写入报告；
- README、运行手册、第三方声明和数据边界文件存在；
- 输出目录可写，且本次运行 ID 尚未存在。

预检失败时不得启动容器。错误只报告稳定原因码、配置字段名和脱敏路径摘要，不回显数据库密码、Bearer Token、API Key 或完整私有路径。

### 3.3 隔离 Compose 编排

使用现有 `db → bootstrap → api → web` 服务拓扑，通过 v0.8 覆盖配置实现：

- 唯一 Compose 项目名与独立命名资源；
- 可配置的宿主机 API 与 Web 端口；
- 默认离线的内部网络，阻止容器直接访问互联网；
- 只读知识包与模型挂载；
- 全新数据库卷和索引卷；
- 可采集的容器健康、退出码、日志与资源统计。

冷启动必须执行无缓存镜像构建，并记录镜像构建、数据库健康、bootstrap 完成、API 就绪和 Web 可访问的耗时。bootstrap 未成功时，API 和 Web 不得被判定为可交付。

### 3.4 HTTP 与浏览器验收

真实 HTTP 验收至少覆盖：

- `/health` 与 `/ready`；
- 普通用户注册、登录和角色边界；
- CNC 合成资产诊断、证据引用、安全和不确定性展示所需数据；
- 无需重启切换到 nXDS10i，且引用不得混入 CNC 包；
- 基于服务端诊断快照创建工单草稿；
- 普通用户越权审批被拒绝；
- approver 或 admin 审批；
- API 重启后使用同一 `thread_id` 恢复并保持唯一最终决定；
- 审计事件存在且不包含敏感值。

真实浏览器使用 Chrome/CDP 操作已经启动的 RC 前端，验证登录、设备选择、双设备切换、诊断结果、证据侧栏、安全/不确定性提示、工单草稿和审批界面。浏览器验收保存脱敏步骤结果和必要截图引用，但不保存密码、Token、厂商手册正文或完整诊断证据文本。

自动化 HTTP 通过不能替代真实浏览器通过；前端单元测试和构建通过也不能替代浏览器验收。

## 4. 离线策略与外部连接边界

发布候选默认运行在不允许互联网出站的内部容器网络中。数据库、API、Web、bootstrap 和受控故障服务在显式 Compose 网络内通信；宿主机只通过发布的本地端口访问 API 与 Web。

离线验证同时使用两层证据：

1. 配置层：`INDUSTRIALOPS_OFFLINE=true`、Hugging Face/Transformers 离线变量和禁用追踪配置均生效；
2. 行为层：把回答服务地址指向本地受控“出站诱饵”，执行诊断后确认诱饵收到零次请求。

LLM 超时和 LLM 错误使用同一内部网络上的本地故障服务模拟，不向真实外部服务发送问题、证据或知识包内容。在线 DeepSeek Judge 不属于 v0.8 强制主链路；v0.7 已保存的 Judge 结果只作为历史评测产物核对，不在 RC 冷启动中隐式重跑。

如果未来启用在线回答，只有显式配置的回答服务地址可以进入允许列表；默认离线配置不得因系统环境中的 API Key 或代理变量而访问外部服务。

## 5. 故障矩阵与预期行为

每个故障场景使用独立的受控资源或明确恢复点，不能污染后续场景。预期失败只有在实际状态、稳定错误码、脱敏日志和恢复结果全部符合契约时才算通过。

| 场景 | 注入方式 | 预期行为 | 恢复验证 |
| --- | --- | --- | --- |
| BGE 或 reranker 缺失 | 指向隔离的空模型目录 | bootstrap 或就绪检查明确失败，指出模型依赖，不尝试联网下载 | 恢复正确只读挂载后 bootstrap 和 `/ready` 通过 |
| 知识包缺失 | 指向隔离的空包目录或缺少一个包 | bootstrap 明确失败，API 不以可交付状态启动 | 恢复两个冻结包后通过哈希校验 |
| 索引损坏 | 只修改本次 RC 的可再生索引卷 | 就绪或 bootstrap 以稳定索引错误拒绝错误索引，不返回错误证据 | 按文档重建本次索引后恢复 |
| 数据库异常 | 停止本次 RC 的数据库容器 | `/health` 仍反映进程存活，`/ready` 和依赖数据库的请求返回明确不可用状态 | 数据库恢复后迁移、数据和 checkpoint 保持一致 |
| LLM 超时 | 内部故障服务延迟超过配置超时 | 诊断走受证据约束的本地降级，记录稳定提供方错误，不生成越界步骤 | 故障服务恢复后受控内部回答测试可正常返回 |
| LLM 错误 | 内部故障服务返回错误或无效响应 | 诊断走相同安全降级，响应和日志不泄露上游正文或凭证 | 恢复后再次调用成功 |
| 离线出站诱饵 | 离线模式配置诱饵地址和伪 Key | 诊断完成且诱饵请求数为零 | 不需要恢复；结果写入离线证明 |

若某故障导致系统返回确定性根因、跨包引用、危险维修步骤、绕过审批或泄露敏感信息，则本次 RC 直接失败，不能仅记录为普通已知限制。

## 6. 基线采样

v0.8 只记录真实观察值，不预设性能通过数字，也不基于一次有利运行挑选结果。

### 6.1 启动时间

记录以下单调时间点及耗时：

- 无缓存镜像构建完成；
- 数据库首次健康；
- bootstrap 完成；
- API 首次 `/ready`；
- Web 首次可访问。

### 6.2 请求延迟

在同一已就绪 RC 环境中，对健康检查、就绪检查、认证、CNC 诊断、真空泵诊断、资产列表和工单详情执行固定次数的预热与采样。报告样本数、成功数、失败数、最小值、中位数、p95 和最大值，并明确回答提供方是本地证据降级还是受控故障服务。

### 6.3 资源与并发

通过 Docker 统计记录每个服务的 CPU、内存和容器状态快照。并发基线使用固定的小规模并发级别和固定场景，记录吞吐、延迟分布、错误数、跨包引用数和安全门禁结果。并发只验证演示环境的观察基线，不宣称生产容量或 SLA。

## 7. 真实性与发布材料审计

真实性审计把公开声明映射到可复现证据，至少检查：

- README 中每项已实现能力是否对应实际 API、界面、测试或验收产物；
- `/api/diagnosis/query` 是否真实经过 LangGraph 主链路；
- Reranker、SafetyPolicyGate、人工审批、离线门控和审计是否真实接入；
- README 中数字是否能定位到冻结输入、报告和生成命令；
- API 文档与当前请求/响应、权限和错误码一致；
- 架构说明与 `db → bootstrap → api → web` 真实拓扑一致；
- `THIRD_PARTY_NOTICES.md`、依赖许可证和外部代码来源完整；
- 厂商资料、项目译文、合成资产、模型生成内容和本地私有模型的身份明确区分；
- 原始手册、派生语料、模型权重、`.env`、数据库、索引和备份不会进入公开镜像或 Git；
- 已知限制、失败样本和未验证能力仍被保留。

审计不使用简单关键词存在作为“能力真实”的唯一证据。关键声明必须绑定代码路径、测试、命令或本次验收报告中的结构化步骤。

## 8. 报告与数据治理

每次运行创建不可覆盖的目录，例如：

```text
data/evaluation/reports/v08/<run-id>/
├── report.json
├── summary.md
├── compose-status.json
├── sanitized-logs/
├── browser-evidence/
└── baseline/
```

`report.json` 是结构化事实源，至少包含：

- 报告格式版本、运行 ID、开始/结束时间和总体状态；
- Git 提交、工作树状态和工具版本；
- 冻结输入与配置的非敏感指纹；
- 各阶段状态、原因码、耗时和证据引用；
- 故障矩阵的注入、观测与恢复结果；
- 启动、延迟、资源和并发原始样本摘要；
- 文档真实性审计结果；
- 未执行、跳过、失败和已知限制。

报告写入必须使用临时文件后原子发布；已存在的运行 ID 一律拒绝覆盖。`summary.md` 只从 `report.json` 生成，不维护第二套事实。日志进入报告前统一脱敏，禁止记录密码、Token、API Key、完整数据库 URL、完整私有路径、厂商手册正文和不必要的用户数据。

仓库只提交不含私有内容的验收摘要、规格、运行手册和必要的小型测试夹具。含本机路径、容器完整日志、截图或私有输入指纹的现场原始产物保持本地，并通过 `.gitignore` 边界管理。

## 9. 错误处理与恢复原则

- 阶段失败后立即停止依赖该阶段的后续步骤，但继续生成部分报告；
- 预期故障与基础设施意外失败使用不同状态和原因码；
- 命令超时后保存退出状态和已脱敏输出，不把超时当作测试通过；
- 恢复步骤只操作本次 RC 的精确项目名、容器或卷；
- 验收器不得自动删除数据库卷、现有项目卷或不属于本次运行的资源；
- 数据库和索引分别治理：数据库优先恢复，索引在输入身份正确时可以重建；
- 任何安全、审批、跨包引用或敏感信息泄露问题都属于发布阻断项。

## 10. 测试策略

所有新增行为严格执行 RED-GREEN-REFACTOR。

### 10.1 自动化测试

先为以下行为编写失败测试并观察预期失败：

- 运行 ID 和资源所有权校验；
- 已存在报告拒绝覆盖与原子写入；
- 命令、环境、日志和错误的脱敏；
- 预检成功与每类明确失败；
- Compose 隔离、只读挂载、内部网络和可配置端口契约；
- 阶段状态机、部分失败报告和稳定原因码；
- 故障矩阵预期结果判定；
- 延迟分位数、资源样本和并发结果统计；
- README 声明与证据映射审计；
- CLI 退出码和机器可读输出。

纯逻辑测试使用真实临时文件、真实本地 HTTP 故障服务和小型夹具。只有 Docker 子进程边界等无法在单元测试中稳定创建的外部接口才使用注入式适配器，测试目标是调用方契约而不是模拟对象本身。

### 10.2 静态与回归验证

- 全仓 Python 测试；
- 前端测试和生产构建；
- `docker compose config` 及 v0.8 覆盖配置解析；
- Docker 镜像中不包含受限资料、模型、`.env`、数据库、索引或备份；
- README、运行手册、API 与许可证文件的一致性检查。

### 10.3 真实发布验收

- 隔离、无缓存 Docker 冷启动；
- 真实 HTTP 双设备与工单主链路；
- 真实 Chrome/CDP 浏览器主链路；
- 全部故障矩阵及恢复；
- 启动、延迟、资源和并发基线；
- 按 README 从零执行安装、启动、演示和评测命令；
- 清理前保留完整脱敏报告，并由操作者核对本次精确资源范围。

## 12. 完成条件

只有以下条件全部满足，v0.8 才能标记为 `release_verified`：

1. 新环境能仅根据 README 完成预检、冷启动和验证；
2. Docker 无缓存构建、全新卷启动、健康/就绪、主链路和全量回归通过；
3. 离线模式的配置证据和零诱饵请求行为证据均通过；
4. 六类故障注入都有明确错误、脱敏日志和成功恢复结果；
5. CNC 与真空泵的真实 HTTP 和浏览器演示均通过且引用隔离；
6. 工单不能绕过人工审批，重启恢复和唯一决定保持有效；
7. 启动、请求、资源和并发基线基于真实原始样本生成；
8. README、API、架构、许可证、版权和合成数据声明与真实系统一致；
9. 报告不可覆盖，失败、跳过、限制和修复记录完整保留；
10. 不存在阻断演示、交付、安全或数据诚信的问题。

v0.8 不创建正式版本标签。通过后的代码、配置、迁移、报告和文档由 v1.0 阶段冻结并发布。
