# v0.4：设备台账、工单与人工审批设计

**日期：** 2026-11-11  
**状态：** `release_verified`（2026-11-12）  
**范围：** 在不修改阶段 0 冻结知识包的前提下，为 IndustrialOps 增加可信设备台账、证据绑定的维修工单、确定性状态机、基于 LangGraph `interrupt()` 的人工审批、可跨服务重启恢复的 SQLAlchemy checkpointer，以及完整的权限和审计链路。

## 1. 目标与完成状态

v0.4 把 v0.3 的证据驱动诊断接入可持久化但不自动执行的维修工单闭环。完成后系统应满足：

- `asset_id` 表示某台具体设备，不能与 `equipment_model_id` 或知识包 ID 混用；
- 工单内容来自服务端保存的诊断结果和引用快照，客户端不能伪造诊断依据；
- 新工单只能以 `draft` 创建，并立即进入等待人工审批的工作流；
- 只有 `approver` 或 `admin` 可以批准或拒绝；
- `draft -> approved` 只能由人工批准产生，其他接口不能绕过；
- 所有非法状态转换均被确定性拒绝；
- LangGraph 在审批点真实中断，并能在服务重启后按 `thread_id` 恢复；
- 审批决定、工单状态变化、操作者和恢复线程均可审计。

完成代码、迁移和全量自动化测试后标记 `automated_verified`。只有在本机 MySQL 上完成迁移、Uvicorn API、服务重启后恢复审批及审计查询的真实验证后，才标记 `release_verified`。

### 1.1 实施验收结论（2026-11-12）

本规格范围内的需求均已完成并验证：`approver`/`admin` 审批、服务端证据快照、确定性状态机、同步 SQLAlchemy checkpoint、`interrupt()`/`Command(resume=...)` 跨重启恢复、版本与权限校验、稳定错误码和全部规定审计动作均已交付。

- 自动化回归：224 项通过；覆盖非法转换、角色权限、checkpoint 全契约、跨 workflow 实例恢复、恢复失败审计，以及并发批准/拒绝仅产生一个最终决定。
- 真实验收：本机 MySQL 8.4.5 从空库升级到 `v04_assets_work_orders`，Uvicorn 在草稿中断后停止并重启；使用原 `thread_id` 恢复审批，确认唯一审批、状态转换、checkpoint 和审计记录持久化。
- 范围边界：Vue 工单工作台、外部 CMMS/EAM 集成、设备控制、库存与预测维护仍是明确非目标，不构成本规格遗漏。

## 2. 已确认决策与边界

### 2.1 已确认决策

- 新增 `approver` 角色，并允许 `admin` 执行同样的批准和拒绝操作。
- 审批状态必须持久化；进程重启后仍能使用同一 `thread_id` 恢复。
- 实现同步 SQLAlchemy checkpointer，并适配 LangGraph `BaseCheckpointSaver`。
- 使用 LangGraph `interrupt()` 暂停，使用 `Command(resume=...)` 恢复；不以普通状态字段模拟中断。
- 生产数据库继续使用 MySQL/PyMySQL，自动化测试使用 SQLite；领域服务和迁移必须兼容两者。
- API 通过数据库型不透明 Bearer 会话解析真实用户和角色，角色不得由请求体或可伪造请求头指定。
- 诊断结果先保存为服务端 `DiagnosisRecord`，工单草稿通过 `diagnosis_request_id` 引用它。
- 数据库设备台账只提供资产上下文，不修改、覆盖或反向推断冻结知识包内容。
- 工单保存诊断和引用快照；知识包未来升级不能静默改变历史工单依据。
- 所有审批和状态变化在事务内同时写入业务记录和审计记录。

### 2.2 为什么本阶段只实现同步 checkpointer

当前 FastAPI 路由、SQLAlchemy `Session`、PyMySQL 驱动和 `DiagnosisWorkflow.invoke()` 均为同步调用。v0.4 只实现当前图执行所需的同步 saver 方法，包括 `get_tuple`、`put`、`put_writes`、`list` 和 `delete_thread`。不引入异步数据库驱动、`AsyncSession` 或第二套异步事务逻辑。

FastAPI 会在线程池中执行同步路由。将来只有在整条应用链路迁移为异步数据库和异步图调用后，才增加 `aget_tuple`、`aput` 等异步实现。

### 2.3 本阶段非目标

- 不实现 v0.5 的 Vue 设备台账、工单审批或诊断工作台页面；
- 不连接真实 CMMS、EAM、MES、SAP 或 Maximo；
- 不向 PLC、CNC 控制器或真空泵下发任何写操作；
- 不实现备件库存、维护计划调度、预测性维护或传感器流；
- 不实现分布式审批队列、异步 checkpointer、跨数据库事务或多区域容灾；
- 不修改冻结知识包、评测集、索引或 v0.2/v0.3 历史报告；
- 不引入知识图谱、图数据库、Graph Agent 或新的多智能体运行时；
- 不复制外部项目的前端、Agent、RAG、预测模型或连接器。

## 4. 总体架构

```text
Bearer 登录
    └─ AuthSessionService
        └─ auth_sessions（仅保存 token 哈希）

设备台账 API
    └─ AssetService
        ├─ EquipmentModel
        └─ Asset

诊断 API
    └─ DiagnosisWorkflow（v0.3）
        └─ DiagnosisRecord + Citation Snapshot

工单 API
    └─ WorkOrderService
        ├─ WorkOrder 状态机
        ├─ WorkOrderTransition
        ├─ ApprovalDecision
        └─ AuditEvent

LangGraph 工单审批图
    ├─ prepare_draft
    ├─ await_human_approval → interrupt()
    ├─ approved / rejected
    └─ SQLAlchemyCheckpointSaver
        ├─ langgraph_checkpoints
        └─ langgraph_checkpoint_writes
```

路由只负责 HTTP、身份解析和错误映射。服务层负责事务、权限、业务校验和查询。领域状态机是纯逻辑，不访问数据库。仓储查询通过 SQLAlchemy `Session` 完成。审批图只编排暂停与恢复，不重新实现工单状态规则。

## 5. 数据模型

### 5.1 `equipment_models`

至少包含：

- `id`：稳定内部主键；
- `equipment_model_id`：公开业务标识，唯一；
- `pack_id`：所属冻结知识包；
- `manufacturer`、`model_name`、可选 `controller_or_firmware_scope`；
- `active`；
- `created_at`、`updated_at`。

`equipment_model_id` 不能等于具体资产编号。`pack_id` 必须与已加载知识包注册表一致，但数据库记录无权修改知识包。

### 5.2 `assets`

至少包含：

- `id`：内部主键；
- `asset_id`：公开且唯一的具体设备编号；
- `equipment_model_id`：外键；
- `display_name`、可选 `site`、`line`、`location`；
- `status`：`available`、`maintenance` 或 `out_of_service`；
- `synthetic`：第一版演示资产固定为 `true`；
- `version`：乐观并发版本；
- `created_at`、`updated_at`。

不保存不存在的实时传感器字段，不把合成资产描述为真实工厂设备。

### 5.3 `diagnosis_records`

至少包含：

- `request_id`：沿用诊断响应 ID，唯一；
- `created_by_user_id`：允许为空，以兼容现有诊断入口；
- `asset_id`、`pack_id`、型号和控制器快照；
- `status`、`intent`；
- 清洗后的请求 JSON、结构化结果 JSON、引用 JSON；
- `knowledge_pack_version`；
- `created_at`。

不得保存 API 密钥、认证头、密码、模型隐藏推理或未经清洗的异常文本。

### 5.4 `work_orders`

至少包含：

- `id`：内部主键；
- `work_order_id`：公开业务标识，唯一；
- `asset_id`、`diagnosis_request_id`；
- `thread_id`：审批图线程，唯一；
- `title`、`description`、`priority`；
- `status`；
- `assigned_to_user_id`；
- 诊断摘要、检查步骤、安全前置条件和引用快照 JSON；
- `created_by_user_id`；
- `version`：乐观并发版本；
- `created_at`、`updated_at`、可选 `completed_at`、`closed_at`。

### 5.5 审批、转换与登录会话

`approval_decisions` 保存工单、`thread_id`、决定、理由、审批人和时间。一个审批线程只允许一个最终决定。

`work_order_transitions` 以追加方式保存前状态、后状态、动作、操作者、原因和时间，不允许修改历史行。

`auth_sessions` 只保存随机 token 的哈希、用户、过期时间、撤销时间和创建时间。明文 token 仅在登录响应中出现一次，日志和审计中不得记录。

### 5.6 LangGraph checkpoint 表

`langgraph_checkpoints` 使用 `thread_id + checkpoint_ns + checkpoint_id` 作为复合唯一键，保存父 checkpoint、序列化类型、checkpoint 二进制和 metadata 二进制。

`langgraph_checkpoint_writes` 使用线程、命名空间、checkpoint、任务、索引和通道形成稳定唯一约束，保存 LangGraph 待处理写入。

checkpoint 使用 LangGraph serializer 的 typed bytes，不使用任意来源的 pickle。表只接受服务端生成的数据。

## 6. 工单状态机与权限

状态转换固定为：

```text
draft --人工批准--> approved --管理员指派--> assigned
assigned --被指派人开始--> in_progress
in_progress --被指派人完成--> completed
completed --approver/admin 审核--> closed

draft/approved/assigned/in_progress --按权限取消--> cancelled
draft --人工拒绝--> cancelled
```

任何未列出的转换都返回 `invalid_work_order_transition`。终态 `closed` 和 `cancelled` 不能再次转换。

角色规则：

- `user`：查看资产和工单、基于允许的诊断创建草稿；被指派后可以开始和完成自己的工单；
- `approver`：拥有普通用户读取能力，可以批准、拒绝和关闭已完成工单；
- `admin`：拥有以上能力，并可维护设备台账、指派和按规则取消工单；
- 只有 `approver` 或 `admin` 可以造成 `draft -> approved`；
- 不允许客户端直接提交目标状态 `approved` 来绕过审批端点。

## 7. 认证和 API 契约

### 7.1 登录

`POST /api/auth/login` 接受用户名和密码，成功时返回不透明 Bearer token、到期时间和公开用户信息。认证失败统一返回 `invalid_credentials`，不泄露用户名是否存在。

受保护接口通过 `Authorization: Bearer <token>` 查找 token 哈希对应的有效会话和用户。缺失、无效、过期或撤销的 token 返回 `401 unauthorized`。

### 7.2 设备台账 API

- `GET /api/equipment/assets`：分页，并可按知识包、型号、状态筛选；
- `GET /api/equipment/assets/{asset_id}`：读取单个资产；
- `POST /api/equipment/assets`：仅 `admin`；
- `PATCH /api/equipment/assets/{asset_id}`：仅 `admin`，使用版本号防止丢失更新。

第一版不提供硬删除。需要移除的资产改为 `out_of_service`，以保留历史工单外键。

### 7.3 工单 API

- `GET /api/work-orders`：分页，并可按资产、状态、审批人或创建人筛选；
- `GET /api/work-orders/{work_order_id}`：返回工单、引用、转换历史和审批结果；
- `POST /api/work-orders/drafts`：基于 `diagnosis_request_id + asset_id` 创建证据绑定草稿；
- `POST /api/work-orders/{work_order_id}/approve`：`approver/admin`；
- `POST /api/work-orders/{work_order_id}/reject`：`approver/admin`，拒绝理由必填；
- `POST /api/work-orders/{work_order_id}/transitions`：执行指派、开始、完成、关闭或取消，并进行角色与状态校验。

创建草稿成功返回 `202`，包含 `work_order_id`、`status=draft`、`approval_status=pending_approval`、`thread_id` 和 interrupt 摘要。

## 8. 诊断到工单的数据流

```text
POST /api/diagnosis/query
→ 执行 v0.3 诊断图
→ 保存 DiagnosisRecord 与引用快照
→ 返回 request_id

POST /api/work-orders/drafts
→ 读取 DiagnosisRecord 和 Asset
→ 校验 pack/model/controller 兼容
→ 校验诊断状态和允许字段
→ 生成 WorkOrder draft
→ 启动审批图
→ await_human_approval 调用 interrupt()
→ checkpoint 与业务记录提交
→ 返回 pending_approval + thread_id

POST .../approve 或 .../reject
→ Bearer 身份解析
→ 检查 approver/admin
→ 锁定工单与审批记录
→ Command(resume=审批决定)
→ 从数据库 checkpoint 恢复
→ 执行 approved 或 rejected 节点
→ 写工单、转换、审批和审计
→ 提交事务
```

只有 `answered` 诊断可以自动带出检查步骤。需要人工升级但没有可执行步骤的诊断可以创建仅包含升级说明的草稿。`blocked`、`out_of_scope`、型号冲突或证据不足的诊断不得自动生成维修步骤；若不满足安全条件，创建草稿请求返回稳定业务错误。

## 9. Checkpointer 和事务一致性

### 9.1 Saver 契约

`SQLAlchemyCheckpointSaver` 继承 `BaseCheckpointSaver`，实现当前同步图实际使用的方法。它接受 `session_factory`，并支持绑定一个调用级 `Session`。

普通读取可以创建短事务。创建草稿和恢复审批时，工作流服务把同一个 `Session` 绑定给 saver，图节点、checkpoint、工单、审批和审计共同使用该会话。Saver 在绑定模式下只 `flush`，不自行 `commit`；由外层服务统一提交或回滚。

### 9.2 中断与恢复

审批图使用唯一 `thread_id` 编译配置。首次调用运行到 `interrupt()`，返回的 interrupt 内容只能包含工单 ID、安全摘要和允许展示的引用信息。

恢复时使用同一 `thread_id` 和 `Command(resume=...)`。服务重启后重新构造图和 saver，从数据库读取 checkpoint 后继续，不依赖进程内对象。

由于 LangGraph 恢复会从中断节点开头重新执行，`interrupt()` 之前不得放置外部副作用。所有状态修改放在批准或拒绝分支中，并通过唯一约束和版本号保持幂等。

### 9.3 并发与幂等

- 批准与拒绝竞争时，审批唯一约束和工单版本号确保只有一个决定成功；
- 对同一最终决定的安全重试返回当前结果，不重复写转换或审计；
- 相反决定返回 `409 approval_already_decided`；
- 版本冲突返回 `409 stale_resource_version`；
- 任一数据库或图执行异常均回滚本次业务事务。

## 10. 审计事件

沿用现有 `audit_events` 表，新增稳定动作名：

- `auth.login_succeeded`、`auth.login_failed`；
- `asset.created`、`asset.updated`；
- `diagnosis.recorded`；
- `work_order.draft_created`；
- `work_order.approval_requested`；
- `work_order.approved`、`work_order.rejected`；
- `work_order.transitioned`；
- `workflow.interrupted`、`workflow.resumed`、`workflow.resume_failed`。

审计 detail 使用结构化、脱敏 JSON，至少记录安全的前后状态、`thread_id`、原因码和操作者。不得记录密码、Bearer token、数据库 URL、API 密钥、完整模型原始响应或异常堆栈。

## 11. 错误处理

HTTP 层统一返回：

```json
{
  "error": {
    "code": "invalid_work_order_transition",
    "message": "The requested work-order transition is not allowed"
  }
}
```

稳定映射：

- `400`：业务输入组合无效；
- `401 unauthorized`：未认证或登录态无效；
- `403 forbidden`：角色或资源权限不足；
- `404 asset_not_found/work_order_not_found/diagnosis_not_found`；
- `409 invalid_work_order_transition/approval_already_decided/stale_resource_version`；
- `422`：Pydantic 字段校验失败；
- `500`：经脱敏的内部错误，不暴露 checkpoint、数据库或凭据内容。

失败响应不得把 SQLAlchemy 异常、数据库 URL、checkpoint 二进制或原始认证信息返回给客户端。

## 12. 数据库迁移

新增 Alembic 依赖与项目配置，首个 v0.4 revision 创建本设计中的业务、认证和 checkpoint 表，并扩展用户角色约束。迁移只操作数据库，不修改知识包文件。

迁移必须满足：

- 从空数据库可升级到 head；
- 对现有 `users` 和 `audit_events` 数据兼容；
- MySQL 和 SQLite 测试数据库均可创建必要约束与索引；
- downgrade 只删除本 revision 创建的对象，不删除既有 v0.1 数据；
- 应用启动不以 `Base.metadata.create_all()` 替代生产迁移。

合成资产通过显式初始化命令导入，不能在模块导入时静默写库。初始化记录必须保留 `synthetic=true` 和知识包关联。

- 诊断、资产与知识包不匹配时不能创建草稿；
- checkpoint 的保存、读取、列出、待处理写入和删除；
- 销毁原 workflow/saver 后，使用同一数据库和 `thread_id` 恢复；
- 重复审批和批准/拒绝竞争不会生成双重决定；
- 工单、转换、审批和审计信息一致；
- 现有 v0.1、v0.2 和 v0.3 测试全部继续通过。

真实发布验收由用户在 Windows PowerShell 5.1 中执行提供的命令，覆盖 MySQL 迁移、Uvicorn、登录、创建草稿、停止服务、重新启动、按 `thread_id` 审批和查询审计。未完成该真实链路时不得写成 `release_verified`。
