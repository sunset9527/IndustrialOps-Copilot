# v0.7：功能闭环与质量收敛设计

**日期：** 2026-11-19  
**状态：** 已获用户批准，待实施计划  
**范围：** 不新增设备、厂商资料或产品功能；基于两个冻结知识包完成工业评测体系、Ragas 与 DeepEval 集成、失败基线、测试先行修复、全量回归和本机真实 API 验证。

## 1. 目标与验收级别

v0.7 的目标不是继续扩展产品，而是证明 v0.1 至 v0.6 已承诺的能力能够被统一、可复现地验证，并修复评测暴露的真实系统问题。

本阶段完成状态分为两级：

- `automated_verified`：四层评测中的自动化门禁和全量测试通过，修复前后结果、失败样本、修复记录和已知限制均已保存；
- 本机真实 API 验证：使用冻结知识包、本地模型、隔离数据库和真实 Uvicorn HTTP 完成双设备诊断及工单闭环。

无缓存 Docker 冷启动、真实浏览器、异常部署、资源与并发基线属于 v0.8，不提前纳入 v0.7。

## 2. 已确认决策与边界

### 2.1 已确认决策

- HeritageMind 的检索、引用、知识缺口和评测治理方法可以迁移，但工业安全、设备兼容、诊断不确定性和人工审批拥有更高优先级。
- 评测采用“确定性规则、RAG 与回答质量、工作流轨迹、人工与 Judge 校准”四层结构。
- 确定性安全、设备兼容和人工审批是硬门禁，不能交给 LLM Judge 决定。
- 原有 `scenario_eval_v1.jsonl` 六条检索题和 `guardrail_eval_v1.jsonl` 五条规则题保持字节级不变，继续作为 v1 冒烟基线。
- v0.7 可建立独立版本的扩展评测集，但只能从现有冻结手册和结构化证据取材。扩展集不得覆盖 v1，不得通过同义改写堆数量，也不得在审核和冻结前用于公开泛化结论。
- 真实接入 Ragas 和 DeepEval，而不是只复刻其指标名称。两者进入独立 `eval` 可选依赖，不进入 API、离线诊断或公共 CI 的默认运行依赖。
- Ragas 负责 RAG 与回答质量的 Judge 指标；DeepEval 负责端到端任务完成和工作流轨迹 Judge 指标。项目原生确定性指标仍是工业硬门禁和可复现基线。
- v0.7 至少保存一次真实 Ragas 与 DeepEval Judge 运行结果。Judge 不可用时可以完成确定性回归，但不能宣称两个框架已完成真实发布验收。
- 现有 `workflow_trace` 继续保留，结构化事件以向后兼容方式增加。事件只记录可观察行为，不记录隐藏思维链。
- 所有修复严格采用测试先行：先保存当前失败基线，再为每个失败补充能稳定复现的失败测试，确认红灯后实施最小修复。

### 2.2 不可变边界

- 不修改 `cnc_pack_v1.0.0` 和 `dry_vacuum_pump_pack_v1.0.0` 的内容、清单或哈希；
- 不补厂商文档、不删题、不修改预期证据迎合系统输出、不降低门禁；
- 不新增设备、控制器、预测性维护、知识图谱、真实设备控制或外部 CMMS 集成；
- 不将合成资产、告警或工单描述为真实工厂数据；
- 不把 LLM 生成内容写入知识包后作为厂商事实；
- 不把 11 条 v1 冒烟题或未完成人工审核的扩展题描述为工业诊断泛化证明。

## 3. 评测体系架构

```text
冻结知识包、注册表、索引与评测集
                │
                ▼
      v0.7 Evaluation Orchestrator
        ├─ Layer 1 确定性规则门禁
        ├─ Layer 2 RAG 与回答质量
        │    └─ Ragas Adapter
        ├─ Layer 3 LangGraph 轨迹
        │    └─ DeepEval Adapter + local trace
        └─ Layer 4 人工与 Judge 校准
                │
                ▼
    逐案例结果 + 指标汇总 + 失败样本
                │
                ▼
 before 报告 → TDD 修复 → after 报告
                │
                ▼
 修复日志 + 已知限制 + v0.7 验收结论
```

评测编排器负责加载版本化场景、校验输入哈希、调用被测入口、收集结构化观察值、计算指标并写入不可覆盖报告。指标计算器不直接修改业务对象，也不允许在运行时更改预期结果。

## 4. 评测数据治理

### 4.1 v1 冒烟基线

v1 的 11 条既有题原样保留。每次报告记录两个文件的 SHA-256，并在运行结束时再次校验。哈希变化时整次评测失败，不生成成功结论。

### 4.2 v0.7 扩展集

扩展场景使用独立文件和版本号，至少包含：

```text
scenario_id
suite_version
knowledge_pack_version
question
asset_context
expected_intent
expected_evidence
forbidden_evidence
expected_safety_actions
expected_workflow_state
expected_work_order_fields
evidence_review_status
evidence_reviewed_by
```

每道内容题必须绑定现有冻结证据的 `evidence_id`、`source_id`、页码和文档修订版。安全、兼容性和审批题可以基于确定性规则及状态机契约，但必须记录规则 ID 或状态转换依据。

扩展遵循“覆盖不同事实和风险，不堆同义问题”的原则，覆盖：

- 五类意图：`manual_query`、`alarm_lookup`、`fault_diagnosis`、`maintenance_plan`、`work_order_draft`；
- 型号缺失、型号不兼容、控制器或修订版冲突、知识域外问题；
- CNC 与真空泵双向串包、相似部件名、数字形态相似的告警码；
- 断电、泄压、上锁挂牌、联锁旁路、未知介质和资质要求；
- 草稿、批准、拒绝、越权、重复或并发审批、非法状态转换和重启恢复。

扩展题先生成候选与证据审核记录，审核通过后再冻结。只有审核通过的题进入正式汇总指标；未审核题保留在候选集，不以失败或成功计分。

### 4.3 历史与数据诚信

- 报告使用时间戳和运行 ID，不覆盖历史文件；
- v1 与扩展集分别汇总，禁止合并后掩盖 v1 退化；
- 失败样本保留原场景 ID、实际输出摘要、期望差异和错误阶段；
- 如果发现冻结知识包事实错误，停止相关修复并按知识包版本规则处理，旧包和旧报告继续保留；
- 人工复核人数不足时明确记录，不生成虚假的一致性指标。

## 5. 第一层：确定性规则门禁

第一层优先运行，任何阻断项失败都会使 v0.7 验收失败，即使其他平均分较高也不能抵消。

### 5.1 设备、型号与版本

计算并逐题保存：

- `Pack Contamination Rate`：不允许包或来源出现在返回引用中的比例；目标为 0；
- `Model Compatibility Accuracy`：型号与控制器接受、补充信息或拒绝决策正确的比例；
- `Revision Match Rate`：引用修订版属于请求兼容范围的比例；
- 允许来源集合符合率和跨设备错误引用数；
- 型号缺失、版本冲突和范围外变体的保守处理率。

兼容性判断以注册表、冻结清单和确定性规则为准，不由回答模型判断。

### 5.2 安全门控

计算：

- `Safety Block Recall`；
- `Over-block Rate`；
- `Escalation Accuracy`；
- `Unsafe Instruction Leakage`；
- `Prompt Injection Bypass Rate`；
- `Safety Prerequisite Coverage`。

危险请求被拦截后，回答的检查步骤、候选原因和自由文本中都不得泄露被禁止的操作方法。安全结论以规则 ID 和人工审核标签为准，LLM Judge 不能覆盖确定性门控结果。

### 5.3 人在回路

必须验证：

- 未审批工单执行率为 0；
- 普通用户越权审批被拒绝；
- 重复或并发批准/拒绝只产生一个最终决定；
- 服务对象重建后可按相同 `thread_id` 恢复；
- 审批前后的诊断与引用快照一致；
- 非法状态转换被稳定错误码拒绝；
- 审批、拒绝、恢复失败和状态变化均有脱敏审计事件。

## 6. 第二层：RAG 与回答质量

### 6.1 检索方法与指标

两个知识包分别运行 BM25、BGE-M3 向量、RRF、CrossEncoder Rerank 和适用时的告警码精确检索，分别报告：

- Source/Page Hit@1、Hit@3、Hit@5；
- MRR、nDCG@5；
- Context Precision、Context Recall；
- 型号过滤正确率和跨包引用数。

逐题排名必须随报告保存，避免汇总指标掩盖失败。真实模型缺失或加载失败时，相关方法标记为运行错误，不能以注入式向量或 0 分替代真实结果。

### 6.2 回答与证据指标

回答评测计算：

- 引用完整率和可定位率；
- `Faithfulness`：回答事实是否能映射到允许证据；
- `Unsupported Root Cause Rate`：候选原因被无依据表述为已确认根因的比例；
- `Inspection Evidence Coverage`：检查步骤中有允许证据支持的比例；
- `Safety Prerequisite Coverage`：必要安全前置条件被覆盖的比例；
- 证据不足时的保守回答率；
- 升级厂商或持证工程师条件的覆盖情况。

可由证据 ID、引用和结构化字段确定的指标使用确定性计算。Answer Relevancy、Answer Correctness 等需要语义判断的指标通过 Ragas Judge 阶段运行，必须与人工标签校准，且不参与安全硬门禁。

### 6.3 Ragas 实际集成

新增 Ragas 适配器，将审核通过的 IndustrialOps 场景映射为 Ragas 本地数据集和实验输入。映射至少包括：

- `user_input`：原始设备运维问题；
- `response`：系统最终回答；
- `retrieved_contexts`：按实际排名返回的证据片段；
- `reference_contexts`：评测题绑定的冻结证据；
- `reference`：经过审核的参考要点，而不是模型临时生成答案；
- IndustrialOps 元数据：场景 ID、包 ID、型号、来源、页码、修订版和运行 ID。

Ragas 真实运行报告以下适用指标：

- Context Precision；
- Context Recall；
- Faithfulness；
- Response/Answer Relevancy；
- Factual/Answer Correctness。

适配器必须显式注入 Judge 和嵌入模型，不允许使用框架默认提供方。Judge 使用项目已有的显式配置，首选与回答模型分离的评测配置；如果只能复用 DeepSeek，报告必须记录模型、参数和“同源模型偏差”限制。Ragas 原始逐题分数、原因或错误随主报告保存，不能只保存平均值。

Ragas 指标不覆盖项目原生 Source/Page Hit、污染率、型号兼容、安全或审批指标。框架缺失、Judge 未配置、请求超时或解析失败时，相关场景标记为 `not_run` 或 `error`，不得写成 0 分或通过。

## 7. 第三层：LangGraph 轨迹与恢复

### 7.1 结构化可观察事件

保留现有 `workflow_trace: tuple[str, ...]`，同时增加结构化事件：

```json
{
  "node": "safety_policy_gate",
  "status": "blocked",
  "duration_ms": 3.8,
  "input_count": 1,
  "output_count": 1,
  "reason": "SAFETY_INTERLOCK_BYPASS"
}
```

事件只包含节点名、状态、时长、计数和稳定原因码。不得保存模型隐藏思维链、密钥、受限证据全文或不必要的用户信息。失败事件保存稳定错误类别，外部报告使用已脱敏信息。

### 7.2 轨迹指标

计算：

- 意图、设备包、型号和控制器路由准确率；
- 预期路径符合率；
- 节点数量、重复节点和无效路径率；
- LLM 失败后的证据降级成功率；
- 证据不足、型号缺失和安全拦截是否走预期短路；
- 工单中断、批准、拒绝和重启恢复成功率；
- 节点耗时和端到端延迟分布。

v0.7 记录真实观测值，不预设延迟目标数字。性能基线与资源门槛留给 v0.8。

### 7.3 DeepEval 实际集成

新增 DeepEval 适配器，在评测模式下将一次诊断工作流调用记录为本地 trace，并将 LangGraph 节点记录为有序 span。至少区分 `agent`、`retriever`、`llm` 和普通工作流节点；span 只传递脱敏输入摘要、输出摘要、计数、状态和原因码。

DeepEval 真实运行至少包含：

- `TaskCompletionMetric`：辅助判断场景目标是否完成；
- `StepEfficiencyMetric`：识别重复检索、无效节点和不必要路径；
- 项目自定义确定性 metric：对比 `workflow_trace` 与场景声明的预期路径、终态和规则 ID。

轨迹评测显式使用本地 tracing，不要求登录或上传到 Confident AI。自动 tracing 默认关闭，只记录项目主动标记的调用，避免收集第三方库和进程中的无关数据。

DeepEval 的内置任务和效率指标属于 Judge 结果；预期路径符合率、短路、安全原因、审批状态和恢复状态仍由项目自定义确定性 metric 裁决。内置 Judge 分数不能把硬门禁失败改成通过。

DeepEval 必须显式注入项目 Judge，不允许回退到框架默认 OpenAI 模型。逐题保存分数、成功状态、原因、错误和 trace 标识；若 Judge 未配置或运行失败，必须如实标记。

## 8. 第四层：人工与 Judge 校准

评测工具提供：

- 去除系统输出偏见的人工复核导出；
- 标注结果导入和字段校验；
- 两名审核者之间的原始一致率、Cohen's Kappa 和分歧样本；
- Judge 输出与人工标签的混淆矩阵及分歧分析；
- Ragas 与 DeepEval Judge 输出的统一导出，不在离线默认路径自动调用外部服务。

人工审核关注证据支持、风险等级、诊断措辞和升级条件。只有真实存在两名独立审核者时才计算 Kappa。单人审核、模型自评或同一回答重复采样不能冒充双人标注。Ragas 与 DeepEval 的 Judge 结果必须分别与人工标签比较，不能合并成一个看似更稳定的平均分。

## 9. 运行器、报告与修复闭环

### 9.1 运行顺序

```text
校验知识包、索引、模型和评测哈希
→ 运行 v1 冒烟基线
→ 运行审核通过的 v0.7 扩展集
→ 运行 Ragas 回答评测与 DeepEval 轨迹评测
→ 计算四层指标并保存 before 报告
→ 逐失败建立回归测试并确认红灯
→ 实施最小修复并确认绿灯
→ 运行全量 Python/前端回归
→ 运行 after 评测
→ 启动真实 Uvicorn 完成本机 HTTP 场景
→ 输出修复日志、失败样本、已知限制和验收结论
```

若当前系统在评测初始化阶段失败，仍保存失败运行记录，包含失败阶段和稳定错误类别；不得因没有完整指标而跳过 before 记录。

### 9.2 报告内容

每份报告至少保存：

- 运行 ID、UTC 时间、Git 提交和配置摘要；
- 评测文件、知识包、注册表、索引和模型指纹；
- 每层逐案例结果、指标分母和汇总值；
- LangGraph 结构化事件和脱敏错误；
- 失败样本与所属门禁；
- 跳过项及其原因；
- 数据集审核状态；
- Ragas、DeepEval 和 Judge 的版本、配置、逐题结果与错误；
- 是否满足 `automated_verified`。

报告不保存 API 密钥、数据库密码、机器用户名、不必要的绝对路径或完整受限手册正文。

### 9.3 修复日志

每个修复条目记录：

- 失败场景和 before 结果；
- 根因所在层：解析、元数据、检索、重排、工作流、安全、接口或展示；
- 新增回归测试及其首次预期失败；
- 最小代码修改；
- after 结果和全量回归状态；
- 未解决限制及其影响。

## 10. 公共 CI 与本地完整评测

公共 CI 使用可公开的小型夹具验证指标公式、场景校验、规则门禁、事件结构和报告格式，不读取私有厂商语料或本地模型权重。

Ragas 与 DeepEval 使用独立的 `eval` 可选依赖组。实现计划开始时以兼容性测试固定已验证版本范围，不让评测框架升级影响 API 默认安装。根据 2026-11-19 官方发布信息，设计基线为 Ragas 0.4.4 与 DeepEval 4.3.4，两者均支持 Python 3.13；最终约束以本项目真实安装和回归结果为准。

本地完整评测显式要求：

- 两个冻结知识包；
- BGE-M3 与 bge-reranker-base 本地路径；
- 已构建且指纹匹配的两个独立索引；
- 审核通过的评测版本；
- 离线模式下不访问外部模型服务；启用 `judge` profile 时才允许访问显式配置的 Judge 地址，并记录提供方、模型、参数和运行错误。

评测运行分成三个 profile：

- `deterministic`：项目原生指标和硬门禁，不调用外部 Judge；
- `framework-smoke`：真实导入 Ragas/DeepEval，使用小型测试夹具验证数据映射、trace 和自定义 metric，不产生语义 Judge 分数；
- `judge`：在审核通过的场景上真实运行 Ragas 与 DeepEval 内置 Judge 指标。

`deterministic` 是 `automated_verified` 的硬门禁；`judge` 结果单独报告，不以平均分替代硬门禁。但 v0.7 要宣称“已实际接入并运行 Ragas/DeepEval”，必须至少完成一次可追溯的 `judge` profile。

私有资产缺失时，公共 CI 的相关集成测试必须明确跳过；完整评测命令则必须失败并说明缺少的依赖，不能输出虚假的完整成功报告。

## 11. 本机真实 API 验证

真实链路使用隔离数据库和独立端口启动 Uvicorn，不污染现有演示数据。验证至少包括：

1. CNC 手册查询、告警查询和故障诊断；
2. 真空泵保养或故障诊断；
3. 双设备引用只来自各自知识包；
4. 型号缺失、版本冲突、知识域外和高风险请求的保守处理；
5. 从已有诊断创建工单草稿；
6. 普通用户不能审批；
7. 审批人批准或拒绝；
8. 服务对象重建后恢复中断流程；
9. 非法状态转换返回稳定错误结构；
10. 审计事件与证据快照一致。

真实 HTTP 结果写入独立验收报告，不以测试客户端结果冒充 Uvicorn 验证。

## 12. 测试策略

所有行为修改遵循 Red-Green-Refactor：

1. **输入治理测试**：v1 哈希不变、扩展题证据定位完整、未审核题不计分；
2. **指标公式测试**：Hit@K、MRR、nDCG、Context Precision/Recall、污染率、覆盖率和 Kappa；
3. **Ragas 适配测试**：字段映射、显式模型注入、逐题结果、错误与跳过语义；
4. **DeepEval 适配测试**：本地 trace、节点 span、显式 Judge、自定义确定性 metric 和错误语义；
5. **安全测试**：拦截召回、误拦截、升级、危险步骤泄露和提示注入；
6. **兼容性测试**：包、型号、控制器、修订版和允许来源；
7. **回答测试**：引用完整性、候选根因措辞、检查步骤证据和证据不足裁剪；
8. **轨迹测试**：事件顺序、状态、原因码、时长、短路、降级和脱敏；
9. **工单测试**：未审批、越权、并发、恢复、快照一致性和非法状态；
10. **报告测试**：不可覆盖、指纹、逐题结果、跳过原因和 before/after 关联；
11. **本地集成测试**：真实知识包、模型、索引、Ragas/DeepEval Judge 和 Uvicorn HTTP；
12. **回归测试**：阶段 0 至 v0.6 的 Python 测试、前端测试和生产构建全部通过。

## 13. 完成标准

v0.7 只有同时满足以下条件才完成：

1. 两个冻结知识包和 v1 评测文件哈希在运行前后保持不变；
2. v1 冒烟基线和审核通过的扩展集均保存逐题结果；
3. 五类意图均有端到端场景覆盖；
4. Pack Contamination Rate 为 0，不存在已知跨设备错误引用；
5. 高风险请求不能绕过确定性安全门控，拦截结果不泄露危险步骤；
6. 证据不足时不生成确定性根因或无证据维修步骤；
7. 工单不能绕过人工审批，越权、重复或并发审批受到约束；
8. LangGraph 轨迹可观察、可脱敏且不保存隐藏思维链；
9. before/after 报告、失败样本、修复日志和已知限制完整；
10. 所有修复均有先失败后通过的回归测试；
11. 全量自动化回归通过，并达到 `automated_verified`；
12. 本机真实 Uvicorn HTTP 双设备与工单闭环验证通过；
13. Ragas 与 DeepEval 均完成真实集成测试，并至少保存一次可追溯 Judge 运行结果；
14. 两个框架的模型、配置、版本、错误和逐题结果可追溯，且均未覆盖工业硬门禁；
15. 未执行的双人标注如实标记，不生成不存在的 Kappa；
16. README 和规划文档只写入可由评测产物复现的结果。

## 14. 框架依据

- [Ragas 官方文档](https://docs.ragas.io/en/stable/getstarted/quickstart/)：本地 Dataset、Experiment、自定义指标以及显式 LLM/Embedding 注入；
- [DeepEval tracing 官方文档](https://deepeval.com/docs/evaluation-llm-tracing)：本地 tracing 与 LangGraph 集成；
- [DeepEval Task Completion](https://deepeval.com/docs/metrics-task-completion) 与 [Step Efficiency](https://deepeval.com/docs/metrics-step-efficiency)：完整轨迹的任务和步骤评测；
- [Ragas 0.4.4](https://pypi.org/project/ragas/) 与 [DeepEval 4.3.4](https://pypi.org/project/deepeval/) 的 Python 版本和许可证元数据；
- 两个框架都只承担评测与观察职责，不进入工业安全和审批决策链。
