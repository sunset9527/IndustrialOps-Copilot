# v1.0 正式发布设计

**日期：** 2026-11-22  
**目标状态：** `v1.0_release_ready`  
**设计依据：** `IndustrialOps Copilot项目规划.md` 的 v1.0 正式发布阶段  
**前置条件：** v0.8 已于 2026-11-22 完成独立 Release Candidate 验收并标记为 `release_verified`

## 1. 目标与边界

v1.0 只冻结并发布已经通过 v0.8 验收的系统，不增加设备、知识、产品页面、业务接口或运行时能力。发布工作必须保留既有失败样本、适用边界和数据身份，不得为改善公开指标修改冻结知识包、评测集或指标口径。

本阶段完成后，本地仓库应达到 `v1.0_release_ready`：代码、数据库迁移、知识包身份、索引配置、评测输入和公开材料已经冻结；最终自动化验证、人工抽查、发布包构建和敏感信息扫描已经通过。该状态不等于已经发布到 GitHub。

以下操作不属于本阶段的自动执行范围：

- 不推送 `origin/main`；
- 不创建或推送 Git 标签；
- 不创建 GitHub Release；
- 不录制 CNC 与真空泵演示视频。演示视频由用户明确决定本次跳过，发布材料不得将其写成已完成。

## 2. 方案选择

采用“清单驱动的冻结发布”：在现有 v0.8 验收体系上增加轻量 v1.0 发布层，而不是新建一套业务或验收框架。

未采用的方案：

1. 仅更新文档并手工压缩：无法可靠证明冻结对象和归档边界，可复现性不足。
2. 仿照 v0.8 新建完整 v1.0 验收框架：会在正式发布阶段引入不必要的代码与回归风险，违背“不再调整功能范围”的约束。

## 3. 发布产物

### 3.1 版本与冻结事实

- 项目公开版本统一为 `1.0.0`；
- v1.0 发布清单记录数据库迁移 head、两个知识包版本、索引配置、评测文件和公开材料；构建器要求工作树干净，并将实际源提交写入构建报告；
- 对仓库内可公开冻结文件记录 SHA-256；
- 对本地私有知识包只记录已有公开身份、版本和经脱敏的完整性依据，不写入绝对路径、原始正文或不可公开指纹；
- 发布清单是 v1.0 冻结事实的唯一结构化来源，文档摘要从清单引用，不维护互相冲突的第二套数字。

### 3.2 公开材料

至少交付：

- 更新后的 `README.md`；
- 与实际拓扑一致的架构说明；
- 数据来源、版权、合成数据、项目译文、模型生成内容和本地模型边界说明；
- 最终评测摘要、复现命令、失败样本和已知限制；
- 第三方代码与数据许可清单；
- `RELEASE_NOTES_v1.0.0.md`；
- 本设计、实施计划和本地发布检查记录。

公开数字必须能定位到冻结输入、脚本或既有不可覆盖报告。v0.7 的两条 Judge 结果继续按原边界陈述，不扩大为在线回答模型、完整 BGE/RRF/reranker 或工业泛化结论。

### 3.3 本地发布包

生成：

```text
dist/
├── IndustrialOps-Copilot-v1.0.0.zip
├── IndustrialOps-Copilot-v1.0.0.zip.sha256
└── v1.0.0-release-build-report.json
```

`dist/` 为本地构建输出，不作为源文件提交。ZIP 只包含允许公开的 Git 跟踪文件，并具有稳定的顶层目录 `IndustrialOps-Copilot-v1.0.0/`。校验文件记录 ZIP 的 SHA-256。构建报告记录源提交、清单身份、文件数量、扫描结果和构建状态，不记录凭据或本机绝对路径。

## 4. 组件设计

### 4.1 发布清单

发布清单至少包含：

- schema 版本与产品版本；
- 发布来源必须是干净工作树，实际 Git 提交由构建报告在构建时记录；
- Alembic head；
- `cnc_pack_v1.0.0` 与 `dry_vacuum_pump_pack_v1.0.0`；
- 设备包注册表和索引配置身份；
- 冻结评测文件及 SHA-256；
- 必需发布材料及 SHA-256；
- 必须执行的验证命令；
- v0.8 RC 公开验收摘要引用；
- 已知限制和明确跳过项。

清单不得包含数据库密码、API Key、Bearer Token、完整数据库 URL、私有资料正文、本地模型权重、绝对路径或本地报告内容。

### 4.2 发布校验器

校验器只负责发布事实，不进入诊断运行时。它检查：

- 版本号与发布清单一致；
- Alembic 只有预期的单一 head；
- 冻结文件存在且哈希一致；
- 两个知识包身份和注册表配置一致；
- README、架构、数据、评测、许可、限制和发布说明齐全；
- 强制验证结果存在且状态为通过；
- 跳过项被明确披露，不能伪装为通过。

任一强制项缺失或不一致时返回非零退出码，不生成合格发布结论。

### 4.3 发布包构建器

构建器以 Git 跟踪文件为输入，不遍历整个工作区后再尝试删除敏感文件。构建前执行允许/排除规则，构建后重新读取 ZIP 目录并进行二次扫描。

以下内容必须排除：

- `.env`、密钥、Token、凭据和本机配置；
- 私有厂商手册及其原始正文；
- 本地模型与权重；
- 数据库、备份、索引和运行卷；
- 本地原始评测报告、完整日志和浏览器截图；
- Python/Node 缓存、测试临时目录和编辑器状态；
- 任何包含本机绝对路径或未脱敏连接串的文件。

如果归档扫描命中阻断规则，构建失败并删除本次不合格 ZIP 与校验文件；源文件不被删除或修改。

### 4.4 发布证据

发布证据记录每条验证命令、开始和结束时间、退出码、状态及脱敏摘要。它引用 v0.8 的公开验收结论，但 v1.0 仍需在最终代码上重新执行全仓回归、前端构建、Compose 配置检查和发布包验证。

本地 v0.8 原始报告继续保留在忽略目录中，不复制进公开发布包。公开材料只引用已经人工核对的脱敏摘要。

## 5. 数据流

```text
v0.8 release_verified 仓库
→ 完成本地发布提交并校验版本与干净工作树
→ 计算冻结对象哈希
→ 校验 v1.0 发布清单
→ 运行最终自动化回归
→ 执行五条主链路人工抽查
→ 核对公开声明、许可和已知限制
→ 从 Git 跟踪文件构建公开 ZIP
→ 扫描归档并验证可解压性
→ 生成 SHA-256 与构建报告
→ 标记本地 v1.0_release_ready
```

人工抽查覆盖：

1. CNC 告警查询；
2. 真空泵维护查询；
3. 两个设备包引用隔离；
4. 高风险操作被安全门控阻断；
5. 工单草稿不能绕过人工审批。

抽查优先复用 v0.8 的隔离运行方式和工具，不操作默认 `industrialops` Compose 项目，不修改冻结知识包、模型或评测输入。

## 6. 失败处理

发布门禁统一 fail-closed：

- 版本、迁移 head、冻结哈希或必需材料不一致：停止；
- Python、前端、生产构建或 Compose 配置失败：停止；
- 主链路抽查失败：保存失败事实并停止；
- 归档含私有资料、凭据模式、模型、数据库、索引、原始手册或本地报告：构建失败，删除本次不合格构建产物后修正规则；
- Docker 或必要本地依赖不可用：标记未完成，不复用旧结果冒充本次通过；
- 发现业务、安全、审批、隔离或数据诚信阻断问题：仅允许进行带回归测试的最小修复，不扩展功能范围；
- 发现知识包事实错误：停止 v1.0，按知识包版本规则处理，不能静默修改已冻结包。

所有失败、跳过和限制保留在发布记录中，不通过删除失败样本或覆盖历史结果获得发布结论。

## 7. 测试与验收

### 7.1 测试先行

发布工具的新增行为遵循 RED-GREEN-REFACTOR。先用失败测试定义：

- 清单 schema 与版本一致性；
- 文件哈希和 Alembic head 校验；
- Git 跟踪文件输入边界；
- 私有文件与敏感内容排除；
- ZIP 二次扫描与可解压性；
- SHA-256 校验文件；
- 缺少证据或存在跳过项时的 fail-closed 行为；
- 构建报告脱敏。

### 7.2 最终自动化验证

必须执行：

- v1.0 发布工具定向测试；
- 全仓 Python 测试；
- 前端 Vitest；
- Vite 生产构建；
- `docker compose config`；
- v1.0 清单校验；
- ZIP 解压、内容边界和 SHA-256 校验；
- README、架构、数据、评测、许可与发布说明链接检查。

### 7.3 完成条件

只有以下条件全部满足，才标记 `v1.0_release_ready`：

1. 版本、代码、迁移、知识包身份、索引配置和评测集已由清单冻结；
2. 所有公开数字均有可复现来源，失败样本和边界仍保留；
3. 最终自动化验证全部通过；
4. CNC、真空泵、隔离、安全和审批五条抽查通过；
5. README 不包含未实现或未验证能力；
6. 发布材料明确区分官方资料、项目译文、合成数据、模型生成内容和本地模型；
7. 第三方代码与数据许可记录完整；
8. ZIP 可解压、SHA-256 一致且不含私有或敏感内容；
9. 演示视频明确记录为本次跳过；
10. 本地推送、标签和 GitHub Release 命令已经准备，但尚未执行。

## 8. 用户后续发布边界

实现完成后只向用户提供经过当前仓库状态校验的本地发布命令。用户亲自决定何时：

1. 检查本地提交和发布包；
2. 推送 `origin/main`；
3. 创建并推送 `v1.0.0` 标签；
4. 创建 GitHub Release 并上传 ZIP 与 SHA-256。

在上述外部操作发生前，任何文档都只能声明“本地发布就绪”，不能声明“v1.0 已在 GitHub 正式发布”。
